# 컨텍스트 스위칭 — 멈춘 일을 기억하고 다른 일 하기

> **한 문장으로:** CPU가 작업을 바꿀 때는 멈춘 작업의 진행 상태를 저장하고 다음 작업의 상태를 꺼냅니다.

## 왜 필요한가요?

컴퓨터에는 CPU가 당장 실행할 수 있는 수보다 더 많은 작업이 있을 수 있습니다. 어떤 작업이 파일이나 네트워크를 기다리는 동안 다른 작업을 진행할 방법이 필요합니다.

## 일상에서 떠올려 보기

상담 직원이 고객 A의 요청을 처리하다가 서류를 기다리게 됐다고 해 보세요. ‘어디까지 처리했는지’를 메모한 뒤 고객 B를 응대하고, 나중에 그 메모를 보고 A의 일을 이어갑니다.

## 순서대로 따라가기

1. 현재 작업의 다음 명령 위치와 계산 상태를 저장합니다.
2. 운영체제가 실행할 수 있는 다른 작업을 선택합니다.
3. 선택한 작업의 상태를 불러와 이전에 멈춘 곳부터 이어갑니다.

```mermaid
flowchart LR
 A["작업 A 진행"] --> B["A 상태 저장"] --> C["B 상태 불러오기"] --> D["작업 B 진행"]
```

## 작은 예로 확인하기

한 사람이 전화 두 통을 번갈아 받는다고 실제로 동시에 두 사람과 말하는 것은 아닙니다. 전환이 빠르면 두 요청이 함께 진행되는 것처럼 보입니다. 운영체제의 도움을 요청하는 시스템 콜을 했다고 해서 반드시 다른 스레드로 바뀌는 것은 아닙니다.

## 처음 만나는 용어

| 용어 | 쉬운 뜻 |
|---|---|
| 실행 문맥 | 작업을 나중에 이어가기 위해 기억해야 하는 상태입니다. |
| 컨텍스트 스위칭 | 한 작업의 실행 문맥에서 다른 작업의 문맥으로 바꾸는 것입니다. |
| 스케줄러 | 어떤 작업을 언제 실행할지 고르는 운영체제 부분입니다. |
| 대기 | 필요한 데이터나 자원을 기다려 당장 실행할 수 없는 상태입니다. |

**비유의 한계:** 작업 전환에도 시간이 들고 가까이 보관하던 데이터의 활용이 떨어질 수 있습니다. 작업 수를 늘리는 것만으로 전체 속도가 증가하지는 않습니다.

## 스스로 확인

시스템 콜로 운영체제에 도움을 요청하면 반드시 다른 스레드가 실행될까요?

**답과 이유:** 아닙니다. 운영체제 권한으로 들어갔다가 같은 스레드의 일을 계속할 수도 있습니다. 권한 모드 전환과 작업 문맥 전환은 구분해야 합니다.
<!-- level:2 -->
# 전환 종류와 관측 단위

<!-- beginner-guide:start -->
## 읽기 전 길잡이

아래 예제는 자신의 작업에서 전환이 얼마나 일어났는지 관찰합니다. 기다리며 넘긴 차례와 실행 시간을 나누며 바뀐 차례를 구분하세요. 모든 전환이 같은 원인이나 비용을 갖지는 않습니다.

## 이 단계에서 만날 말

| 용어 | 쉬운 뜻 |
|---|---|
| 레지스터 상태 | CPU 안에 있던 계산값과 실행 위치 정보입니다. |
| 준비 큐 | 실행할 수 있지만 CPU 차례를 기다리는 작업들의 목록입니다. |
| 모드 전환 | 일반 프로그램 권한과 운영체제 권한 사이를 이동하는 것입니다. |
| 자발적 전환 | 작업이 대기하는 등의 이유로 실행 자리를 넘기는 것입니다. |
| 비자발적 전환 | 운영체제가 실행 시간을 나누기 위해 다른 작업으로 바꾸는 것입니다. |
| ASID·PCID | 주소 공간을 구별해 주소 변환 정보를 활용하도록 돕는 식별 기능입니다. |

<!-- beginner-guide:end -->

스케줄러는 실행 가능한 태스크 중 대상을 고른다. 대기 상태의 태스크는 준비 큐에서 실행을 기다리는 태스크와 다르다. 같은 프로세스의 스레드끼리 주소 공간을 공유할 수 있지만 각자의 실행 문맥은 다르다. 다른 주소 공간으로의 전환에서는 페이지 테이블 관련 상태도 달라질 수 있다. TLB 영향은 아키텍처와 ASID/PCID 같은 기능에 따라 달라지므로 항상 전체 TLB를 비운다고 단정하지 않는다.

Linux에서 자기 프로세스의 전환 횟수를 확인하는 Python 3 예제다.

```python
import resource, time
before = resource.getrusage(resource.RUSAGE_SELF)
for _ in range(10):
    time.sleep(0.001)
after = resource.getrusage(resource.RUSAGE_SELF)
print("voluntary", after.ru_nvcsw - before.ru_nvcsw)
print("involuntary", after.ru_nivcsw - before.ru_nivcsw)
```

정확히 10회의 전환을 보장하지는 않는다. OS 스케줄링과 다른 태스크에 의해 결과가 달라진다. voluntary는 실행 주체가 기다리는 등의 이유로 양보한 전환, involuntary는 선점 등에 따른 전환으로 해석할 수 있다. 서버에서는 전체 시스템 수치뿐 아니라 특정 워커·스레드와 요청 지연을 연결해 보아야 한다.

**실습:** sleep 간격과 CPU 작업을 바꿔 두 종류의 전환이 어떻게 달라지는지 기록하자. 전환 자체의 순수 비용을 측정한 실험이라고 주장하지 않는다.

# 가상 장애 — 워커 200개가 코어 4개를 경쟁한다

<!-- beginner-guide:start -->
## 읽기 전 길잡이

작업자는 많이 만들었는데 CPU가 실제 일보다 차례를 바꾸는 데 시간을 쓸 수 있습니다. 전환 횟수뿐 아니라 실행 대기와 실제 처리량을 함께 보며 원인을 좁혀 보세요.

<!-- beginner-guide:end -->

CPU 중심 작업을 처리하는 워커 수를 크게 늘린 뒤 지연이 악화된 사례를 재현한다. 실행 가능한 스레드 수가 코어 수를 훨씬 넘으면 준비 큐 대기와 캐시 재가열이 커질 수 있다. 다만 I/O 중심 작업에는 다른 적정 동시성이 필요하다.

Linux 학습 서버에서 `pidstat -w -p PID 1`, `vmstat 1` 등으로 전환과 실행 큐를 확인한다. CPU 사용률·스레드 수·p95 지연·처리량을 같은 부하에서 함께 기록한다. 높은 voluntary 전환이 정상적인 입출력 대기를 나타내는지, 락 경합을 나타내는지도 스택 샘플과 연결한다.

**수정:** CPU 워커 풀을 제한하고 유입 큐에 길이 제한·타임아웃·백프레셔를 둔다. 무조건 스레드 수를 코어 수와 똑같이 고정하기보다 실제 작업의 대기 비율을 측정한다. 바쁜 폴링이나 작은 작업을 지나치게 나누는 코드도 점검한다.

**재검증:** 동시성을 단계적으로 바꿔 처리량이 포화되는 지점과 지연 증가 구간을 찾는다. 큐 길이와 거절률까지 비교해야 과부하를 단순히 다른 장소에 옮기는 실수를 피한다.

# 동시성 모델과 스케줄링 비용

<!-- beginner-guide:start -->
## 읽기 전 길잡이

동시에 처리할 작업 수를 정할 때는 코어 수와 기다리는 시간, 작업 크기를 봅니다. 많은 작업을 작게 나누는 이득과 전환 비용의 균형을 비교하세요.

<!-- beginner-guide:end -->

| 모델 | 장점 | 설계 책임 |
|---|---|---|
| 요청당 OS 스레드 | 동기 코드와 디버깅이 익숙함 | 스택 메모리·전환·풀 제한 |
| 이벤트 루프 | 많은 I/O 연결의 대기를 효율적으로 관리 | CPU 작업 격리·블로킹 방지 |
| 사용자 수준 태스크 | 많은 논리 작업을 적은 스레드에 매핑 | 런타임 스케줄러·취소·관측 |

코어 수보다 많은 작업이 존재해도 적정 동시성은 I/O 대기, 메모리 사용, 런타임과 공정성에 따라 정한다. 컨테이너 CPU 할당량과 실제 호스트 코어 수가 다를 수 있으므로 하드웨어 숫자만 사용하지 않는다. CPU throttling과 스케줄러 대기도 함께 본다.

**판단 연습:** 이미지 변환과 네트워크 호출이 섞인 API를 어떤 풀로 나눌까? 각 풀의 최대 동시성, 큐 상한, 취소 정책, 요청 기한을 제시하고 평균 지연뿐 아니라 꼬리 지연과 실패율을 기준으로 비교하자.
