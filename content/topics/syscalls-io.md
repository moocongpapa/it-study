# 시스템 콜과 입출력 — 운영체제에 일을 부탁하기

> **한 문장으로:** 프로그램은 파일 읽기나 데이터 전송을 운영체제에 요청하고, 완료를 기다리는 방법을 선택합니다.

## 왜 필요한가요?

앱이 하드웨어와 파일을 마음대로 다루면 다른 프로그램의 데이터를 해칠 수 있습니다. 운영체제가 권한과 자원을 확인하면서 대신 처리하는 경계가 필요합니다.

## 일상에서 떠올려 보기

도서관 이용자가 창고에 직접 들어가기보다 직원에게 책을 요청한다고 생각해 보세요. 직원 앞에서 받을 때까지 기다릴 수도 있고, 준비됐는지 나중에 확인할 수도 있습니다. 요청과 기다림을 구분하면 입출력 방식이 보입니다.

## 순서대로 따라가기

1. 프로그램이 읽거나 쓰고 싶은 대상과 데이터 크기를 지정합니다.
2. 시스템 콜로 운영체제에 요청하고 권한과 처리 상태를 확인받습니다.
3. 즉시 처리할 수 없다면 기다리거나, 아직 준비되지 않았다는 결과를 받아 다른 일을 진행할 수 있습니다.

```mermaid
flowchart LR
 A["앱의 읽기 요청"] --> B["운영체제 확인"] --> C["파일·네트워크 처리"]
 C --> D["데이터 또는 아직 준비 안 됨"]
```

## 작은 예로 확인하기

책 10권을 요청했는데 지금 3권만 준비될 수 있습니다. 네트워크 읽기도 요청한 크기보다 적은 데이터를 돌려줄 수 있습니다. 논블로킹 방식은 준비되지 않았을 때 계속 기다리기보다 그 상태를 즉시 알릴 수 있습니다.

## 처음 만나는 용어

| 용어 | 쉬운 뜻 |
|---|---|
| 시스템 콜 | 프로그램이 운영체제 기능을 요청하는 통로입니다. |
| I/O(입출력) | 파일·화면·네트워크 등과 데이터를 읽고 쓰는 작업입니다. |
| 블로킹 | 요청이 처리될 때까지 현재 작업이 기다리는 방식입니다. |
| 논블로킹 | 즉시 처리할 수 없는 상태를 바로 돌려줄 수 있는 방식입니다. |

**비유의 한계:** ‘준비됐다’는 신호가 요청 전체의 완료를 보장하지는 않습니다. 논블로킹과 비동기도 같은 뜻이 아니며, 일부만 읽거나 오류가 나는 경우를 다뤄야 합니다.

## 스스로 확인

논블로킹 읽기에서 데이터가 아직 없으면 어떤 결과를 받을 수 있을까요?

**답과 이유:** 계속 기다리는 대신 아직 처리할 수 없다는 상태를 즉시 받을 수 있습니다. 앱은 다른 일을 하거나 준비 신호를 기다린 뒤 다시 시도할 수 있습니다.

# 부분 읽기·쓰기와 readiness

<!-- beginner-guide:start -->
## 읽기 전 길잡이

아래 예제는 연결 두 개를 만들고 읽을 준비가 됐는지 확인합니다. ‘준비 여부’, ‘실제로 읽은 양’, ‘메시지가 완성됐는지’를 따로 보세요. 이 세 가지를 하나로 생각하면 데이터가 잘릴 수 있습니다.

## 이 단계에서 만날 말

| 용어 | 쉬운 뜻 |
|---|---|
| 소켓 | 네트워크 데이터를 주고받는 연결 지점입니다. |
| 바이트 스트림 | 메시지 경계 없이 이어진 바이트의 흐름입니다. |
| readiness | 현재 읽기나 쓰기를 시도할 준비가 됐는지 나타내는 상태입니다. |
| 프레이밍 | 이어진 데이터에서 메시지의 시작과 끝을 구분하는 규칙입니다. |
| 이벤트 루프 | 준비된 작업을 확인하고 차례로 처리하는 반복 구조입니다. |
| 백프레셔 | 받는 쪽이 감당할 수 있을 만큼 보내는 속도를 조절하는 것입니다. |

<!-- beginner-guide:end -->

TCP 소켓은 바이트 스트림이다. 한 번의 send가 한 번의 recv와 대응하지 않는다. read는 요청 길이보다 적은 바이트를 반환할 수 있고 write도 일부만 보낼 수 있다. 0바이트 반환, 오류, 재시도 가능한 조건을 계약에 따라 처리한다. 메시지는 길이 접두사나 구분자 등 별도 프레이밍이 필요하다.

Python 3에서 소켓쌍의 readiness를 확인하는 실행 가능한 예제다.

```python
import socket, selectors
a, b = socket.socketpair()
a.setblocking(False)
selector = selectors.DefaultSelector()
selector.register(a, selectors.EVENT_READ)
b.sendall(b"hello")
for key, _ in selector.select(timeout=1):
    print(key.fileobj.recv(1024))  # b'hello'
selector.close(); a.close(); b.close()
```

이 작은 예제는 송신이 작아 단순하게 보이지만 일반 서버에는 입력 누적 버퍼, 출력 미전송 버퍼, 연결별 상태와 상한이 필요하다. Linux epoll의 edge-triggered 모드에서는 읽기 가능 통지를 받았을 때 일반적으로 EAGAIN까지 처리해 준비 상태를 비워야 한다. readiness 통지 이후에도 경쟁이나 상태 변화로 즉시 읽을 수 없는 경우를 처리한다.

**실습:** 메시지를 여러 조각으로 보내 길이 접두사 기반 수신기를 만들고 최대 메시지 크기를 검증하자.

# 가상 장애 — 연결은 살아 있는데 수신이 멈춘다

<!-- beginner-guide:start -->
## 읽기 전 길잡이

응답이 느릴 때 CPU 계산 때문인지 외부 데이터를 기다리기 때문인지 구분합니다. 대기 중인 연결과 쌓인 요청을 관찰하고, 느린 상대가 전체 서버를 붙잡지 않도록 기한과 속도 조절을 확인하세요.

<!-- beginner-guide:end -->

가상 edge-triggered 서버가 통지마다 recv를 딱 한 번만 호출해 읽을 데이터가 남았다. 이후 새 readiness 전이가 기대대로 발생하지 않아 응답이 멈춘 것처럼 보일 수 있다.

먼저 연결 상태, 수신 버퍼, 이벤트 등록과 실제 읽기 횟수를 확인한다. Linux에서는 격리된 학습 프로세스에 `strace -e trace=network,read,write -p PID`를 사용할 수 있다. 추적은 성능에 영향을 줄 수 있으며 데이터 원문이 노출되지 않도록 주의한다.

**수정:** 논블로킹 소켓에서 읽기를 반복하다 EAGAIN/EWOULDBLOCK에 도달하면 다음 이벤트를 기다린다. 한 연결이 이벤트 루프를 독점하지 않도록 처리량 예산과 공정성을 고려한다. 쓰기는 미전송 부분을 남겨 다음 준비 이벤트에서 이어 보낸다. 무한 재시도 루프로 CPU를 태우지 않는다.

**재검증:** 조각난 입력, 느린 클라이언트, 절반 닫기, 큰 응답, 취소를 재현한다. 열린 연결 수뿐 아니라 출력 큐 바이트·이벤트 루프 지연·요청 타임아웃을 관측한다.

# I/O 모델과 운영 비용

<!-- beginner-guide:start -->
## 읽기 전 길잡이

요청마다 기다리는 작업자를 둘지, 준비된 연결만 처리할지 선택하는 내용입니다. 연결 수와 실제 작업량, 구현 복잡도에 따라 적합한 방식이 달라집니다.

<!-- beginner-guide:end -->

| 선택 | 장점 | 비용 |
|---|---|---|
| 블로킹 + 제한된 스레드 풀 | 흐름과 오류 처리가 단순 | 대기 스레드와 스택 자원 |
| readiness 이벤트 루프 | 다수 소켓 대기를 효율적으로 관리 | 상태 머신·부분 처리·공정성 |
| completion 기반 API | 완료 이벤트 중심 처리 | 버퍼 수명·취소·플랫폼 차이 |

연결 수만으로 모델을 선택하지 않는다. 요청당 CPU, 실제 동시 대기, 응답 크기, 라이브러리의 블로킹 여부, 팀의 디버깅 능력을 함께 본다. 이벤트 루프 안에 느린 파일 읽기나 CPU 연산을 넣으면 다수 요청의 꼬리 지연을 높일 수 있다.

대형 서버에서 가장 중요한 제약은 **제한된 큐와 백프레셔**다. 소켓이 빠르게 받는다고 처리기가 같은 속도로 처리하는 것은 아니다. 연결별·전역 버퍼 상한, 읽기 중단 조건, 기한과 종료 시 정리를 설계한다. 빠른 경로의 처리량뿐 아니라 느린 소비자와 과부하에서 메모리가 제한되는지를 검증한다.

참고: [Linux epoll](https://man7.org/linux/man-pages/man7/epoll.7.html), [Python selectors](https://docs.python.org/3/library/selectors.html).
