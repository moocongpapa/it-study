# MLOps·LLMOps와 모델 수명주기

> **먼저 한 문장:** 모델 운영은 학습 코드뿐 아니라 데이터·평가·배포·관측·재학습을 하나의 변경 흐름으로 연결하는 일입니다.

노트북에서 잘 작동한 모델도 실제 서비스에서는 자료와 환경이 계속 바뀝니다. 학습·배포·평가·운영을 연결하는 흐름을 알면 시범 결과를 지속 가능한 서비스로 옮길 수 있습니다.

## 먼저 알아둘 말

```learning
{"slug":"mlops-lifecycle","view":"words"}
```

## 작은 예로 이해하기

판매 예측 모델을 만들었다고 일이 끝나지 않습니다. 어떤 자료와 설정으로 만들었는지 기록하고, 서비스에 배포한 뒤 새 판매 자료에서도 맞는지 관찰합니다. 품질이 나빠지면 다시 평가하고 교체하거나 이전 버전으로 돌아갑니다. 이 수명주기 전체를 반복 가능하게 운영하는 일이 MLOps입니다.

## 익숙한 장면과 연결하기

식당에서 새 요리법을 만든 뒤 재료 공급·품질 검사·판매·고객 반응까지 관리하는 것과 같습니다. 레시피 파일만 있으면 영업이 끝나는 것이 아닙니다.

**비유의 한계 — 이 점은 달라요:** 파이프라인 자동화가 모델 품질과 안전을 보장하지는 않습니다. 자료 변화·평가·사람 판단이 필요한 경계는 별도 책임으로 유지합니다.

## 직접 확인하기

학습·검증 → 배포 → 관찰·개선 순서로 읽어 보세요. 뒤의 과정에서 필요한 것이 앞에서 어떻게 준비되는지 찾습니다. 숫자는 읽는 순서이며 모든 상황이 정확히 세 단계라는 뜻은 아닙니다.


## 구체적인 사례와 확인 방법

같은 증상에도 원인이 여럿일 수 있어요. 먼저 발생 조건을 기록하고 증상을 재현할 수 있는지 확인하세요. **관찰한 증상 → 확인할 자료 → 수정 → 수정 후 확인(같은 조건으로 재검증)**을 연결해서 읽습니다.

<!-- classroom-reference:start -->
실제 고객의 장애 기록이 아닌 학습용 재현 시나리오입니다. 결과만 바꾸기 전에 관측한 증거와 원인 가설을 구분합니다.

## 1. 어떤 문제가 생겼나요?

가상 배포 뒤 어떤 학습 자료로 만든 모델인지 찾을 수 없습니다.

## 2. 먼저 확인할 증거

모델 등록 정보·학습 실행·자료 스냅샷·배포 기록을 대조합니다.

## 3. 원인 가설

모델 파일만 복사하고 전체 생성 조건을 연결하지 않았습니다.

## 4. 수정 방법

릴리스에 자료·코드·전처리·평가 버전을 묶습니다.

## 5. 재검증

임의 릴리스에서 학습 조건과 평가·복구 산출물을 추적할 수 있는지 확인합니다.

## 놓치기 쉬운 조건

파이프라인 자동화가 모델 품질과 안전을 보장하지는 않습니다. 자료 변화·평가·사람 판단이 필요한 경계는 별도 책임으로 유지합니다.

## 읽기 전 길잡이

같은 개념도 업무의 규모, 오류 비용, 운영 역량에 따라 적용 방식이 달라집니다. 아래 비교는 특정 제품의 성능 순위가 아닌 선택 기준입니다.
