# 토큰·문맥 창·잘림과 생성 길이

> **오늘의 질문** · AI의 책상에도 펼칠 수 있는 종이 수가 정해져 있을까?

먼저 그림을 눌러 바꿔 볼까요? 답이 달라지는 모습을 천천히 관찰해 보세요.

```learning
{"slug":"tokens-context-windows","view":"explore"}
```

## 익숙한 장면과 연결해요

가방에 자료를 넣을 때 종이 장수만 볼 것이 아니라 실제 부피와 돌아올 때 넣을 물건의 공간도 남겨야 하는 것과 비슷합니다.

## 선생님과 한 번 정리해요

문서를 길게 넣었는데 앞부분을 놓치거나 답이 잘리는 일이 있습니다. 모델이 읽고 쓸 수 있는 양의 제한을 알면 중요한 정보를 배치하고 비용과 실패를 줄일 수 있습니다.

**한 줄로 말하면:** 모델은 글자 수가 아닌 토큰으로 입력과 출력을 다루며 문맥 예산을 넘으면 필요한 정보가 누락되거나 요청이 실패할 수 있습니다.

```learning
{"slug":"tokens-context-windows","view":"words"}
```

**비유의 한계도 알아둘까요?** 글자·단어와 토큰은 일대일 관계가 아닙니다. 문맥 한도가 크다고 모든 위치의 정보를 항상 정확히 활용하는 것도 아닙니다.

```learning
{"slug":"tokens-context-windows","view":"recall"}
```

# 한 장면씩 원리를 따라가요

이번에는 **토큰으로 나누기 → 문맥 예산 → 잘림·생성** 순서로 살펴볼게요. 먼저 다음에 무슨 일이 생길지 생각하고, 그림을 한 칸씩 넘겨 보세요.

```learning
{"slug":"tokens-context-windows","view":"trace"}
```

## 여기서 연결해 봐요

모델은 글자 수가 아닌 토큰으로 입력과 출력을 다루며 문맥 예산을 넘으면 필요한 정보가 누락되거나 요청이 실패할 수 있습니다.

왜 이런 순서가 필요한지 말로 설명할 수 있으면 좋아요. 코드와 자세한 설명은 아래에 준비했어요. 낯선 기호는 입력·바뀌는 값·결과로 나눠 읽어 봐요.

<!-- classroom-reference:start -->
## 읽기 전 길잡이

모델은 글자 수가 아닌 토큰으로 입력과 출력을 다루며 문맥 예산을 넘으면 필요한 정보가 누락되거나 요청이 실패할 수 있습니다. 아래 예제는 외부 시스템에 연결하지 않는 작은 학습용 사례입니다. 입력, 처리 조건, 결과를 순서대로 살펴보세요.

1. 사용 모델의 토큰화·입출력 한도를 확인합니다.
2. 지시·대화·검색 문서와 출력에 쓸 예산을 나눕니다.
3. 잘림·요약 손실·입력 위치별 응답 품질을 검사합니다.

## 예제로 확인하기

```python
limit,instructions,history,retrieval,output=1000,100,300,400,250
total=instructions+history+retrieval+output
assert total>limit
print("예산 초과:",total-limit)
```

## 결과를 해석하기

가상의 토큰 한도에서 계획한 합계는 1050이라 50을 줄여야 합니다. 실제 API의 입력·출력 제한과 과금 방식은 제공자 문서와 토크나이저로 확인합니다. 숫자는 특정 모델 사양이 아닙니다.

## 실무에 옮기기 전

글자·단어와 토큰은 일대일 관계가 아닙니다. 문맥 한도가 크다고 모든 위치의 정보를 항상 정확히 활용하는 것도 아닙니다. 실제 업무에서는 길이뿐 아니라 필요한 근거가 실제 포함되는지 평가합니다. 출력에 필요한 공간과 도구 응답 크기도 예산에 포함하고 조용한 잘림을 관측 가능하게 만듭니다.

## 확인 질문

예제에서 초과한 예산은?

**답과 이유:** 계획 합계 1050과 한도 1000의 차이는 50입니다.

# 오늘은 문제를 찾는 탐정이에요

```learning
{"slug":"tokens-context-windows","view":"debug"}
```

## 해결 뒤에도 한 번 더

고친 다음 원래 입력으로 다시 확인하는 일을 **재검증**이라고 해요. 한 번 성공한 것만 보고 끝내지 않고, 비슷한 실패 조건에서도 괜찮은지 확인해요.

실제 고객의 장애 기록이 아닌 학습용 재현 시나리오입니다. 결과만 바꾸기 전에 관측한 증거와 원인 가설을 구분합니다.

## 1. 어떤 문제가 생겼나요?

가상 긴 문서 요약에서 마지막의 예외 조건이 빠집니다.

## 2. 먼저 확인할 증거

입력 토큰 수와 실제 전송된 본문, 잘림 위치를 확인합니다.

## 3. 원인 가설

길이 제한으로 중요한 부분을 잘라내거나 요약 과정에서 잃었습니다.

## 4. 수정 방법

구조별 분할·명시적 예산·핵심 조건 검증을 적용합니다.

## 5. 재검증

문서 앞·중간·뒤에 필요한 조건을 둔 사례로 누락률을 확인합니다.

## 놓치기 쉬운 조건

글자·단어와 토큰은 일대일 관계가 아닙니다. 문맥 한도가 크다고 모든 위치의 정보를 항상 정확히 활용하는 것도 아닙니다.

## 확인 질문

```learning
{"slug":"tokens-context-windows","view":"decide"}
```

## 이유까지 말하면 더 좋아요

“나는 이 방법을 골랐어. 중요한 조건은 이것이고, 대신 이런 부담은 감수할게.”처럼 설명해 보세요. 그러고 나서 조건을 하나 바꾸면 같은 선택을 할지도 생각해 봐요.
