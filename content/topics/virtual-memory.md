# 가상 메모리 — 각 프로그램이 가진 주소 지도

아파트의 “101호”라는 번호는 도시 전체에서 유일하지 않다. 건물 정보와 함께 실제 위치를 찾는다. 프로세스가 쓰는 주소도 그 프로세스의 주소 공간 안에서 의미를 가진다. 가상 메모리는 프로그램이 보는 주소와 실제 RAM 위치를 분리해 보호·공유·배치를 관리한다. 디스크를 RAM처럼 쓰는 기능만을 뜻하지 않는다.

```mermaid
flowchart LR
  A["프로세스의 가상 주소"] --> B["TLB / 페이지 테이블"]
  B --> C["물리 메모리 프레임"]
  B --> D["권한 오류 또는 페이지 폴트"]
```

운영체제는 주소 공간을 페이지 단위로 관리하고 물리 메모리의 프레임에 연결한다. 다른 프로세스의 같은 가상 주소가 같은 물리 위치를 뜻할 필요는 없다. 반대로 공유 메모리는 서로 다른 주소 공간이 같은 물리 페이지를 가리키도록 구성할 수 있다.

**비유의 한계:** 주소 변환은 매번 사람이 지도책을 찾는 방식으로만 일어나지 않는다. CPU는 TLB에 변환 결과를 캐시한다. 페이지 폴트도 항상 디스크 읽기를 뜻하지 않으며 처음 접근한 익명 페이지 할당이나 권한 오류 등 다양한 원인이 있다.

**확인:** 가상 주소 공간 크기, 실제 상주 메모리, swap 사용량을 왜 각각 구분해야 할까?

# 주소 변환과 첫 접근을 추적하기

가상 주소는 페이지 번호와 페이지 내부 오프셋으로 나뉜다. TLB 적중이면 변환을 빠르게 얻고, 미스면 페이지 테이블을 확인한다. 페이지가 유효하지 않거나 권한 조건을 만족하지 않으면 예외가 발생해 커널이 처리한다. 필요한 페이지를 준비할 수 있으면 명령을 재개하고, 불법 접근이면 프로세스에 신호 등을 전달한다.

Python 3와 Linux에서 익명 매핑을 만드는 학습 예제다. 페이지 크기는 실행 환경에서 조회한다.

```python
import mmap, os
page = os.sysconf("SC_PAGE_SIZE")
size = page * 1024
region = mmap.mmap(-1, size)
for offset in range(0, size, page):
    region[offset] = 1  # 첫 쓰기가 실제 페이지 준비를 유발할 수 있음
print("mapped bytes", size, "page bytes", page)
region.close()
```

실행 전후 `resource.getrusage`의 page fault 통계나 Linux 프로세스의 `smaps_rollup`을 관찰할 수 있다. 구체적 카운트는 OS와 기존 접근 상태에 따라 달라진다. Copy-on-write는 페이지를 처음부터 모두 복사하지 않고 쓰기 시점에 별도 사본을 만드는 기법이다. 이 역시 쓰기가 많아지면 물리 메모리 비용이 늘어난다.

**실습:** 매핑만 한 단계와 페이지마다 쓰는 단계를 나눠 관측하자. “malloc 성공”과 “모든 페이지가 RAM에 상주”는 같은 보장이 아니다.

# 가상 장애 — RSS가 증가하고 응답 지연이 흔들린다

가상 배치 서비스에서 큰 배열을 확보한 뒤 처음 데이터를 채울 때 지연이 급증했다고 하자. 할당 API 시간만 측정하면 실제 첫 페이지 접근 비용을 놓칠 수 있다. 먼저 RSS, minor/major page fault, swap 입출력, cgroup 메모리 제한을 함께 본다.

```text
illustrative: allocation returned quickly
illustrative: first-touch phase has increased page faults
```

minor fault 증가만으로 디스크 병목이라고 결론 내리지 않는다. major fault와 저장장치 입출력을 대조하고, CPU/NUMA 배치와 파일 매핑 접근도 구분한다. 운영체제의 메모리 회수나 컨테이너 한도에 의해 OOM이 발생했는지 로그를 확인한다. 접근하지 않는 큰 가상 매핑을 메모리 누수로 단정하지 않는다.

**수정:** 워킹셋과 동시 배치를 제한하고 데이터를 청크로 처리한다. 필요한 경우 준비 단계에서 첫 접근을 수행하되 시작 지연과 메모리 한도를 고려한다. 무조건 swap을 끄는 처방은 피한다.

**재검증:** 같은 데이터량에서 첫 요청과 정상 상태의 p95, RSS, fault 종류를 따로 비교한다. 예열이 OOM 위험을 높이지 않는지도 확인한다.

# 주소 공간을 활용하는 설계 선택

| 선택 | 이득 | 부담 |
|---|---|---|
| 익명 메모리 | 일반 데이터 구조를 간단히 구성 | 워킹셋·회수 비용 |
| 파일 mmap | 파일을 주소 공간으로 접근 | 첫 접근 폴트·수명·일관성 주의 |
| 명시적 read/write | 입출력 시점과 버퍼 제어 | 복사와 호출 관리 |
| 큰 페이지 | TLB 효율 개선 가능 | 내부 낭비·할당·운영 복잡성 |

메모리 예산은 프로세스별 힙만 더하지 않는다. 스레드 스택, 페이지 테이블, 파일 캐시, 런타임, 공유 메모리, 컨테이너 회계 규칙을 포함한다. 주소 공간이 크다는 사실이 물리 메모리 부족을 없애 주지 않는다. NUMA 환경에서는 같은 RAM도 접근 코어와 위치에 따라 비용이 달라진다.

**판단 연습:** 큰 읽기 전용 파일을 다수 워커가 사용하는 서비스에서 mmap과 명시적 버퍼 읽기를 비교하자. 예측 가능한 지연이 필요한지, 랜덤 접근인지, 오류 처리와 파일 교체를 어떻게 할지 근거를 남긴다.

참고: [Linux mmap](https://man7.org/linux/man-pages/man2/mmap.2.html), [Linux proc_pid_smaps](https://man7.org/linux/man-pages/man5/proc_pid_smaps.5.html).
