# 데이터 소유권·계약·계보

> **먼저 한 문장:** 누가 데이터를 책임지고 어떤 변환을 거쳐 어디에 쓰이는지 알아야 변경과 사고의 영향을 추적할 수 있습니다.

숫자가 어디서 왔는지, 누가 써도 되는지 모르면 믿고 활용하기 어렵습니다. 자료의 담당자와 이동 경로·사용 조건을 남기면 오류를 추적하고 필요한 사람에게 확인할 수 있습니다.

## 먼저 알아둘 말

```learning
{"slug":"data-governance-lineage","view":"words"}
```

## 작은 예로 이해하기

주간 보고서의 ‘활성 사용자’가 갑자기 늘었습니다. 원본 로그인 기록부터 중복 제거, 날짜 변환, 집계 과정을 따라가면 어디서 기준이 바뀌었는지 찾을 수 있습니다. 이 연결 기록이 계보입니다. 각 표의 책임자와 변경 약속까지 있어야 영향을 받는 사람에게 알릴 수 있습니다.

## 익숙한 장면과 연결하기

식재료의 원산지와 유통 경로를 기록하는 일과 같습니다. 문제가 생겼을 때 어느 요리에 쓰였는지 알아야 필요한 범위에 대응할 수 있습니다.

**비유의 한계 — 이 점은 달라요:** 계보가 있다고 데이터가 항상 정확한 것은 아닙니다. 자동 수집되지 않는 수작업 변환도 있고, 기록 자체에도 접근 권한과 갱신 책임이 필요합니다.

## 직접 확인하기

원본·담당자 → 이동·변경 → 권한·추적 순서로 읽어 보세요. 뒤의 과정에서 필요한 것이 앞에서 어떻게 준비되는지 찾습니다. 숫자는 읽는 순서이며 모든 상황이 정확히 세 단계라는 뜻은 아닙니다.

같은 증상에도 원인이 여럿일 수 있어요. 먼저 발생 조건을 기록하고 증상을 재현할 수 있는지 확인하세요. **관찰한 증상 → 확인할 자료 → 수정 → 수정 후 확인(같은 조건으로 재검증)**을 연결해서 읽습니다.

실제 고객의 장애 기록이 아닌 학습용 재현 시나리오입니다. 결과만 바꾸기 전에 관측한 증거와 원인 가설을 구분합니다.

## 1. 어떤 문제가 생겼나요?

가상 원본 컬럼 이름 변경 뒤 여러 리포트가 동시에 깨집니다.

## 2. 먼저 확인할 증거

컬럼의 상하위 모델, 사용 팀, 최근 배포와 계약 검증 결과를 확인합니다.

## 3. 원인 가설

사용처를 모른 채 호환성 없는 변경을 했습니다.

## 4. 수정 방법

대체 컬럼과 이전 기간을 두고 계약 검증·변경 통보 절차를 만듭니다.

## 5. 재검증

의존 리포트와 모델을 회귀 검사하고 계보에서 누락된 수작업을 찾습니다.

## 놓치기 쉬운 조건

계보가 있다고 데이터가 항상 정확한 것은 아닙니다. 자동 수집되지 않는 수작업 변환도 있고, 기록 자체에도 접근 권한과 갱신 책임이 필요합니다.
