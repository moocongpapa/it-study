# 객체지향 — 데이터와 지켜야 할 행동을 한곳에 모으기

> **한 문장으로:** 객체는 상태와 행동을 함께 묶어, 정해진 규칙으로 데이터를 다루게 하는 설계 단위입니다.

## 왜 필요한가요?

여러 코드가 계좌 잔액이나 주문 상태를 마음대로 바꾸면 업무 규칙이 깨집니다. 상태를 바꾸는 통로와 책임을 분명하게 만들 필요가 있습니다.

## 일상에서 떠올려 보기

은행 창구에서 출금 절차를 거치지 않고 누구나 장부를 고칠 수 있다면 위험합니다. 계좌 객체는 장부와 출금 절차를 함께 두고, 잔액 확인 같은 규칙을 거쳐 값을 바꾸도록 합니다.

## 순서대로 따라가기

1. 함께 다룰 데이터와 행동을 객체로 묶습니다.
2. 상태를 바꾸는 통로에서 유효한 입력과 업무 규칙을 확인합니다.
3. 다른 코드는 내부 저장 방식보다 공개한 행동의 약속을 사용합니다. 여러 구현도 같은 약속을 지키며 교체할 수 있습니다.

```mermaid
flowchart LR
 A["출금 요청"] --> B["계좌 객체"] --> C["잔액·규칙 확인"] --> D["허용된 상태 변경"]
```

## 작은 예로 확인하기

계좌 객체에 withdraw(출금)를 요청하면 금액과 잔액을 확인하도록 만들 수 있습니다. 캡슐화는 이름 앞에 private을 붙이는 일만 뜻하지 않습니다. 외부에서 내부 장부를 그대로 고칠 수 있게 돌려주면 보호하려던 규칙이 깨질 수 있습니다.

## 처음 만나는 용어

| 용어 | 쉬운 뜻 |
|---|---|
| 캡슐화 | 데이터를 정해진 행동 경계로 다루게 하는 것입니다. |
| 추상화 | 사용에 필요한 기능을 드러내고 내부 세부사항은 감추는 것입니다. |
| 상속 | 기존 타입의 관계와 기능을 확장하는 방식입니다. |
| 다형성 | 같은 기능 약속으로 여러 구현을 사용할 수 있는 성질입니다. |

**비유의 한계:** 은행 창구 비유가 실제 보안을 자동으로 제공한다는 뜻은 아닙니다. 객체 경계와 접근 권한은 별도로 설계해야 합니다. 상속을 많이 쓰는 것만으로 좋은 객체지향 설계가 되지도 않습니다.

## 스스로 확인

외부 코드가 내부 잔액 값을 마음대로 바꿀 수 있다면 캡슐화의 목적이 지켜질까요?

**답과 이유:** 업무 규칙을 보호하기 어렵습니다. 상태를 바꾸는 검증된 행동 경계를 사용하도록 하고 가변 내부 자료를 노출하지 않는지 확인해야 합니다.

# 불변식과 대체 가능한 계약

<!-- beginner-guide:start -->
## 읽기 전 길잡이

계좌 예제에서 입력 검사와 잔액 변경이 어디에 모였는지 보세요. 메서드 이름보다 호출 전후에 무엇이 보장되는지 먼저 읽으면 객체의 책임이 보입니다.

## 이 단계에서 만날 말

| 용어 | 쉬운 뜻 |
|---|---|
| 상태 | 객체가 현재 갖고 있는 데이터입니다. |
| 불변식 | 객체의 행동 전후에 지켜야 하는 규칙입니다. |
| 계약 | 입력 조건·결과·오류·상태 변화에 대한 약속입니다. |
| 인터페이스 | 사용할 수 있는 기능의 약속을 표현한 경계입니다. |
| 대체 가능성 | 다른 구현으로 바꿔도 호출자가 기대한 약속을 지키는 것입니다. |
| 구성 | 여러 객체를 함께 사용해 기능을 만드는 방식입니다. |

<!-- beginner-guide:end -->

캡슐화는 필드를 private으로 표시하는 것만으로 끝나지 않는다. 객체가 외부에 가변 내부 리스트를 그대로 돌려주면 보호 경계가 깨질 수 있다. 계약에는 입력 조건·반환 결과·오류·상태 변화가 포함된다.

Python 3의 간단한 계좌 예제다. 금액은 정수 최소 단위로 제한한다.

```python
class Account:
    def __init__(self, balance):
        if balance < 0: raise ValueError("negative balance")
        self._balance = balance
    @property
    def balance(self): return self._balance
    def withdraw(self, amount):
        if amount <= 0 or amount > self._balance:
            raise ValueError("invalid withdrawal")
        self._balance -= amount

a = Account(100)
a.withdraw(30)
assert a.balance == 70
```

Python의 밑줄은 관례이며 보안 샌드박스가 아니다. 이 객체도 동시 요청·DB 영속성·거래 기록을 구현하지 않는다. 상속 관계에서 자식이 부모 계약을 좁히거나 호출자가 예상하지 못한 결과를 내면 대체 가능성이 깨진다. 조합은 객체가 다른 객체의 기능을 사용하는 방식으로, 변경 방향에 따라 상속보다 적합할 수 있다.

# 가상 장애 — 새 구현이 기존 호출자를 깨뜨린다

<!-- beginner-guide:start -->
## 읽기 전 길잡이

특정 구현으로 바꾼 뒤 기존 코드가 깨진 상황을 봅니다. 입력 제한이나 결과·오류 약속이 달라졌는지, 내부 상태를 외부에서 수정할 수 있었는지 조사하세요.

<!-- beginner-guide:end -->

가상 저장소 계약은 “없는 키에는 None을 반환”인데 새 구현은 예외를 던진다. 호출자는 기존 계약으로 작성되어 장애를 일으킨다. 클래스 구조가 비슷한 것과 행동 계약이 같은 것은 다르다.

**진단:** 모든 구현에 동일한 계약 테스트를 적용한다. 입력 경계, 빈 데이터, 오류·취소, 순서·수명 조건을 확인한다. mock이 성공 경로만 흉내내면 차이를 놓칠 수 있다.

**수정:** 계약을 명확히 하고 구현을 맞추거나 변경을 버전으로 드러낸다. 외부 라이브러리의 차이를 어댑터로 정규화할 수 있다. 단지 상속을 삭제한다고 업무 불변식 문제가 해결되는 것은 아니다.

**재검증:** 기존 호출자 테스트와 각 구현의 통합 테스트를 실행한다. 가변 내부 상태가 반환값을 통해 노출되는지도 검사한다.

# 클래스보다 변경 경계를 선택하기

<!-- beginner-guide:start -->
## 읽기 전 길잡이

상속으로 묶을지 작은 객체를 조합할지 비교합니다. 변경 이유, 테스트 범위, 서로 기대하는 약속을 기준으로 설계 선택을 설명해 보세요.

<!-- beginner-guide:end -->

| 선택 | 유리한 상황 | 부담 |
|---|---|---|
| 상속 | 안정된 공통 행동 계약 | 깊은 계층·대체 가능성 |
| 조합·위임 | 독립 기능을 교체 | 객체 연결·설정 복잡성 |
| 함수·불변 데이터 | 단순 변환·계산 | 상태 수명 경계 별도 설계 |

객체 경계는 업무 규칙, 상태 소유권, 변경 빈도에 맞춘다. 서비스 규모가 커질 때 객체 모델을 그대로 네트워크 마이크로서비스로 바꾸지 않는다. 원격 호출은 실패·지연·부분 완료라는 추가 계약을 갖는다.

**판단 연습:** 할인 정책이 자주 바뀌고 주문 저장은 안정적이라면 어느 책임을 객체·함수·인터페이스로 분리할까? 결합도와 테스트 계약을 근거로 결정하자.
