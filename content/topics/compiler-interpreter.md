# 컴파일러와 인터프리터 — 사람이 쓴 코드를 실행으로 연결하기

> **한 문장으로:** 소스 코드를 다른 실행 형태로 번역하거나, 실행 중 해석하는 과정으로 컴퓨터가 일을 하게 만듭니다.

## 왜 필요한가요?

사람은 이름과 문장이 있는 코드가 편하지만 CPU는 정해진 기계 명령을 실행합니다. 사람이 쓴 코드와 실제 실행 사이를 연결하는 도구가 필요합니다.

## 일상에서 떠올려 보기

외국어 조리법을 미리 번역해 요리사에게 주거나, 요리하며 필요한 부분을 통역하는 상황을 떠올려 보세요. 미리 바꾸는 과정이 컴파일에, 실행 중 해석하는 과정이 인터프리팅에 가깝습니다.

## 순서대로 따라가기

1. 소스 코드의 단어와 문장 구조를 읽고 잘못된 표현을 확인합니다.
2. 구현에 따라 기계 코드나 중간 실행 형태로 번역합니다.
3. 준비된 형태를 실행하거나 실행 중 추가로 해석·번역합니다. 한 프로그램 안에서 여러 방식을 함께 사용할 수 있습니다.

```mermaid
flowchart LR
 A["사람이 쓴 소스 코드"] --> B["읽기·검사·번역"] --> C["실행 가능한 형태"] --> D["프로그램 실행"]
```

## 작은 예로 확인하기

Python 코드를 실행하면 중간 형태인 바이트코드로 바꾼 뒤 실행하는 구현이 있습니다. 일부 실행 환경은 자주 쓰는 부분을 실행 중 기계 코드로 바꾸기도 합니다. 그래서 한 언어를 ‘번역만’ 또는 ‘해석만’ 하는 것으로 단정하면 실제 구현을 놓칠 수 있습니다.

## 처음 만나는 용어

| 용어 | 쉬운 뜻 |
|---|---|
| 소스 코드 | 개발자가 프로그래밍 언어로 작성한 명령입니다. |
| 컴파일러 | 코드를 다른 실행 형태로 번역하는 도구입니다. |
| 인터프리터 | 코드나 중간 명령을 실행하면서 해석하는 구현입니다. |
| 바이트코드 | 실행 환경이 이해하는 중간 명령 형태입니다. |

**비유의 한계:** 사람의 통역과 달리 코드 처리에는 정해진 문법과 실행 규칙이 있습니다. 언어 이름만으로 처리 방식을 확정할 수 없고 실제 실행 환경을 확인해야 합니다.

## 스스로 확인

하나의 실행 환경에서 컴파일과 인터프리팅을 함께 사용할 수 있을까요?

**답과 이유:** 가능합니다. 먼저 중간 코드로 번역하고 이를 해석하거나, 자주 실행되는 부분을 실행 중 다시 번역하는 방식이 있습니다.

# 파싱에서 실행으로

<!-- beginner-guide:start -->
## 읽기 전 길잡이

아래 예제는 Python 코드가 어떤 바이트코드로 바뀌는지 관찰합니다. 세부 명령 이름을 외우기보다 입력을 읽고 계산한 뒤 결과를 돌려주는 흐름을 찾아보세요.

## 이 단계에서 만날 말

| 용어 | 쉬운 뜻 |
|---|---|
| 토큰화 | 코드를 이름·숫자·기호 등의 조각으로 구분하는 것입니다. |
| 파싱 | 코드 조각을 문장 구조로 분석하는 것입니다. |
| 중간 표현 | 분석·변환을 위해 잠시 사용하는 코드 형태입니다. |
| 링커 | 여러 코드와 외부 함수 연결을 합치는 도구입니다. |
| 로더 | 실행할 내용을 메모리와 실행 환경에 준비하는 부분입니다. |
| JIT | 실행 중 필요한 코드를 기계 코드로 번역하는 방식입니다. |

<!-- beginner-guide:end -->

소스를 토큰화·파싱해 구문 구조를 만들고 이름·타입 등 의미를 분석한다. 구현에 따라 중간 표현을 최적화하고 대상 기계 코드나 바이트코드를 만든다. 링커는 심벌과 코드·데이터를 결합하고 로더는 실행 환경에 놓는다. 각 단계의 오류는 책임이 다르다.

Python 3에서 실행 가능한 바이트코드 관찰 예제다.

```python
import dis
def add(a, b):
    return a + b
dis.dis(add)
assert add(2, 3) == 5
```

출력 명령은 Python 버전에 따라 달라진다. 명령 이름을 영구 계약으로 암기하지 말고 소스 연산이 어떤 실행 단계로 바뀌는지 본다. JIT는 실행 중 프로파일에 맞춰 최적화할 수 있지만 가정이 깨지면 deoptimization이 발생할 수 있다. 인터프리터도 캐시·전문화 같은 최적화를 사용한다.

**실습:** 같은 함수를 워밍업 전후로 측정하고, 실행 시간 외에 시작 시간과 메모리도 기록하자. 소스 줄 하나와 기계 명령 하나가 항상 대응하지 않는다.

# 가상 장애 — 배포 직후만 느리고 이후 빨라진다

<!-- beginner-guide:start -->
## 읽기 전 길잡이

문법을 읽는 중 실패한 것인지, 외부 함수를 연결하지 못한 것인지, 실행 중 오류가 난 것인지 구분합니다. 같은 ‘코드가 안 된다’도 실패 단계에 따라 조사할 대상이 다릅니다.

<!-- beginner-guide:end -->

가상 JIT 서비스가 워밍업 동안 컴파일·클래스 로딩·캐시 준비 비용을 낸다. 모든 시작 지연을 JIT 탓으로 돌리지 말고 의존성 로딩, 네트워크, DB 풀 준비를 분해한다. 동일 요청의 처음과 정상 상태를 따로 측정한다.

**진단:** 런타임 프로파일과 컴파일 로그, GC, CPU, 코드 경로 분포를 연결한다. 벤치마크가 결과를 사용하지 않아 최적화로 제거되는지도 확인한다. 단일 마이크로벤치마크를 전체 API 성능으로 일반화하지 않는다.

**수정:** readiness 이전의 제한된 준비 작업, AOT 대안, 워커 교체 속도와 캐시 준비를 비교한다. 대표하지 않는 예열 데이터가 실제 코드 경로를 덜 준비할 수도 있다.

**재검증:** 차가운 시작, 장기 실행, 입력 타입 변화, 배포 중 용량을 확인한다. p95 지연과 시작 메모리·CPU 비용을 함께 본다.

# 실행 전략을 고르는 기준

<!-- beginner-guide:start -->
## 읽기 전 길잡이

시작 속도, 오래 실행할 때의 속도, 배포 방식, 관찰과 디버깅 비용을 비교합니다. 번역 방식 하나만으로 전체 프로그램 성능을 단정하지 마세요.

<!-- beginner-guide:end -->

| 방식 | 장점 | 비용 |
|---|---|---|
| AOT | 예측 가능한 시작과 배포 산출물 | 대상별 빌드·동적 최적화 제약 |
| JIT | 실제 실행 정보 활용 | 워밍업·코드 메모리·재최적화 |
| 인터프리터/VM | 이식·도구·동적 동작 | 실행 오버헤드·런타임 의존 |

선택은 CPU 처리량뿐 아니라 시작 지연, 메모리 한도, 플러그인 유연성, 빌드 시간, 디버깅과 보안 패치 운영을 포함한다. 서버리스의 짧은 수명과 장기 실행 서버는 워밍업 비용의 비중이 다르다.

**판단 연습:** 매번 짧게 실행되는 CLI와 하루 종일 반복 연산하는 서버에서 같은 실행 전략이 유리할까? 언어 이름보다 구체적 구현·버전을 비교하자.

참고: [CPython dis](https://docs.python.org/3/library/dis.html), [LLVM Language Reference](https://llvm.org/docs/LangRef.html).
