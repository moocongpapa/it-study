# 리팩터링 — 하는 일은 유지하며 읽기 쉽게 고치기

> **한 문장으로:** 외부에서 보이는 동작을 유지하면서 내부 이름과 구조를 이해하기 좋게 개선합니다.

## 왜 필요한가요?

코드의 의미를 이해하지 못하면 작은 수정도 위험합니다. 계산·입출력·예외 처리가 뒤섞인 부분을 정리하면 다음 변경을 검토하기 쉬워집니다.

## 일상에서 떠올려 보기

가게의 상품과 가격은 그대로 두고 창고의 이름표와 배치를 정리한다고 생각해 보세요. 손님이 받는 결과를 바꾸지 않으면서 직원이 물건을 찾고 실수 없이 처리하기 쉬워집니다.

## 순서대로 따라가기

1. 현재 어떤 입력에 어떤 결과가 나오는지 먼저 기록하고 확인합니다.
2. 한 번에 작은 이름 변경이나 함수 분리처럼 범위를 좁혀 고칩니다.
3. 바꾸기 전후의 결과와 오류 처리가 같은지 확인하며 다음 개선으로 진행합니다.

```mermaid
flowchart LR
 A["현재 행동 확인"] --> B["작게 구조 개선"] --> C["결과 비교"] --> D["다음 개선"]
```

## 작은 예로 확인하기

배송비를 계산하는 숫자 3000에 이름을 붙이고, 계산 부분을 함수로 분리할 수 있습니다. 이 과정에서 배송비 조건까지 바꿨다면 기능 수정도 섞인 것입니다. 어떤 동작을 유지하고 어떤 문제를 따로 수정할지 분명하게 기록합니다.

## 처음 만나는 용어

| 용어 | 쉬운 뜻 |
|---|---|
| 클린 코드 | 읽는 사람이 의미와 책임을 이해하기 쉬운 코드를 지향하는 표현입니다. |
| 리팩터링 | 보이는 행동을 유지하며 내부 구조를 개선하는 것입니다. |
| 회귀 | 변경 때문에 이전에 잘 되던 동작이 깨지는 것입니다. |
| 테스트 | 입력과 결과가 기대한 규칙에 맞는지 확인하는 절차입니다. |

**비유의 한계:** 창고 정리처럼 보이는 수정도 숨은 의존성과 예외 처리를 바꿀 수 있습니다. 현재의 버그까지 영원히 유지하자는 뜻은 아니며, 버그 수정은 별도 의도와 검증을 분명히 합니다.

## 스스로 확인

리팩터링 중 할인율까지 바꿨습니다. 내부 구조만 개선한 것일까요?

**답과 이유:** 동작 변경이 섞였습니다. 할인율 변경은 사용자에게 보이는 계산 결과를 바꾸므로 의도와 확인 범위를 별도로 정해야 합니다.
<!-- level:2 -->
# 작은 함수 추출과 계약 테스트

<!-- beginner-guide:start -->
## 읽기 전 길잡이

예제는 배송비 계산의 이름과 단위를 드러냅니다. 코드를 옮긴 뒤에도 같은 입력에 같은 결과가 나오는지 보고, 계산과 외부 저장을 나누는 이유를 생각해 보세요.

## 이 단계에서 만날 말

| 용어 | 쉬운 뜻 |
|---|---|
| 계약 | 코드가 입력과 결과·오류에 대해 지켜야 하는 약속입니다. |
| characterization test | 현재 동작을 관찰해 기록하는 테스트입니다. |
| 순수 계산 | 입력으로 결과를 만들고 외부 상태를 바꾸지 않는 계산입니다. |
| 함수 추출 | 한 역할의 코드를 이름 있는 별도 함수로 옮기는 것입니다. |
| 기술 부채 | 현재 구조 때문에 다음 변경에 추가로 드는 비용을 설명하는 표현입니다. |
| 인지 비용 | 코드를 이해하기 위해 생각해야 하는 부담입니다. |

<!-- beginner-guide:end -->

먼저 현재 행동을 테스트로 고정한다. 레거시의 이해되지 않는 동작에는 characterization test가 도움을 줄 수 있지만 알려진 버그를 영원히 계약으로 굳히지는 않는다. 순수 계산을 추출하면 검증하기 쉬워진다.

Python 3 예제는 배송비 계산을 이름과 단위로 드러낸다.

```python
def shipping_fee(subtotal_won, is_remote):
    if subtotal_won < 0: raise ValueError("negative subtotal")
    base_won = 0 if subtotal_won >= 50_000 else 3_000
    remote_won = 2_000 if is_remote else 0
    return base_won + remote_won
assert shipping_fee(49_999, False) == 3_000
assert shipping_fee(50_000, False) == 0
assert shipping_fee(50_000, True) == 2_000
```

함수 추출, 이름 변경, 조건 정리 등 한 종류를 작은 단위로 수행한다. 변경 전에 오류·경계·부작용 순서를 정하고, 바뀐 호출 관계가 성능을 악화시키지 않는지 확인한다. 인위적인 추상화로 호출이 여러 파일에 흩어지면 이해 비용이 증가할 수 있다.

# 가상 장애 — 리팩터링 후 경계 금액만 잘못 계산된다

<!-- beginner-guide:start -->
## 읽기 전 길잡이

정리 후 일부 입력에서 결과가 달라지는 상황을 봅니다. 경계값과 오류 처리, 호출 순서에 숨은 의존성이 있었는지 전후 결과로 확인하세요.

<!-- beginner-guide:end -->

가상 수정에서 `>= 50000`을 `> 50000`으로 바꾸어 무료배송 경계가 틀렸다. 코드 스타일만 검사하면 찾을 수 없다. 변경 전후의 실제 입력과 결과·오류를 비교한다.

**진단:** 정확한 경계, 경계 바로 아래·위, 빈 값과 잘못된 입력을 테스트한다. 계산 함수와 DB·메일 같은 효과를 분리하면 원인 범위를 줄일 수 있다. 테스트가 구현의 조건문을 그대로 복사하면 같은 오류를 놓칠 수 있다.

**수정:** 계약에 맞는 비교를 복원하고 의미가 드러나는 테스트 이름을 붙인다. 버그 수정과 구조 변경을 커밋으로 구분하면 리뷰와 rollback이 쉬워진다.

**재검증:** 정상·오류·경계 동작과 운영에서 중요한 지연·조회 횟수를 확인한다. 관련이 없는 전면 재작성으로 검증 범위를 늘리지 않는다.

# 개선의 범위와 위험을 고르기

<!-- beginner-guide:start -->
## 읽기 전 길잡이

전체를 다시 쓸지 조금씩 개선할지 비교합니다. 변경 빈도, 현재 오류 위험, 팀이 검토할 수 있는 크기, 점진적 배포 가능성이 판단 재료입니다.

<!-- beginner-guide:end -->

| 접근 | 장점 | 위험 |
|---|---|---|
| 작은 지속 리팩터링 | 검증·리뷰·복구 쉬움 | 장기 구조 변경에 시간 필요 |
| 경계별 점진 이행 | 구·신 구현 비교 가능 | 임시 호환 계층 |
| 전면 재작성 | 모델 재정비 기회 | 숨은 계약·기능 누락·긴 이행 |

대형 시스템의 클린 코드는 팀이 자주 바꾸는 경로와 운영 실패를 기준으로 평가한다. 가독성·테스트 용이성·성능·API 호환성은 함께 고려한다. 코드가 아름답다는 주관만으로 출시 위험을 정당화하지 않는다.

**판단 연습:** 자주 바뀌는 가격 계산과 안정적인 파일 포맷 파서를 모두 다시 쓸 것인가? 변경 빈도·버그 비용·검증 가능성을 근거로 우선순위를 정하자.
