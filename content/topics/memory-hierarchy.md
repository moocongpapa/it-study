# 캐시 메모리와 메모리 계층 · 작동 원리

아래 실험에서는 같은 데이터라도 어떤 순서로 접근하는지 봅니다. 실행 시간에는 Python 자체의 비용도 섞여 있습니다. 숫자를 CPU 캐시만의 속도로 읽기보다 접근 순서가 왜 중요한지 이해하세요.

## 예제와 내부 동작

아래 자료를 읽을 때 **입력 → 바뀌는 값이나 상태 → 결과**를 찾아보세요. 모르는 말은 밑줄 표시를 눌러 뜻을 확인할 수 있어요.

<!-- classroom-reference:start -->
캐시 조회에서 데이터가 있으면 hit, 없으면 miss다. 단순 평균 접근 시간은 `hit_time + miss_rate × miss_penalty`로 근사할 수 있지만 여러 요청이 겹치는 현대 CPU의 실행 전체를 완벽히 설명하는 공식은 아니다. 캐시 라인에는 주소를 식별하는 태그와 상태가 있고, 주소 일부로 세트가 선택된다. associativity는 한 세트에 놓을 수 있는 후보 수와 관련된다.

아래 Python 3 실험은 접근 순서를 보여 주는 학습 예제다. Python 실행 비용도 포함되므로 결과를 CPU 캐시의 순수 지연이라고 해석하지 않는다.

```python
from array import array
from time import perf_counter
values = array("I", range(200_000))
for stride in (1, 16, 256):
    indices = range(0, len(values), stride)
    start = perf_counter()
    total = sum(values[i] for i in indices)
    visits = len(indices)
    print(stride, visits, total, (perf_counter() - start) / visits)
```

비교할 때 방문 원소 수가 달라지는 것을 기록해야 한다. 엄밀한 캐시 비교에는 동일 접근 수·컴파일 조건과 프로파일러가 필요하다. 쓰기에서는 write-through와 write-back, 쓰기 할당 정책 등도 비용에 영향을 준다. 여러 코어가 같은 라인을 수정하면 캐시 일관성 통신이 생긴다. 공유하지 않는 변수도 같은 라인에 놓이면 **false sharing**이 발생할 수 있다.

**실습:** 구조체 배열과 필드별 배열의 접근 패턴을 설명하고 실제 사용하는 필드만 읽는 작업에서는 어떤 배치가 유리할지 가설을 세우자.

# 캐시 메모리와 메모리 계층 · 문제 해결

작업자를 늘렸는데 오히려 느려지는 상황을 봅니다. 서로 다른 작업자가 가까운 메모리 위치를 바꾸면서 캐시 사본을 조정하는 비용이 커질 수 있다는 점을 따라가세요.

## 구체적인 사례와 확인 방법

같은 증상에도 원인이 여럿일 수 있어요. 먼저 발생 조건을 기록하고 증상을 재현할 수 있는지 확인하세요. **관찰한 증상 → 확인할 자료 → 수정 → 수정 후 확인(같은 조건으로 재검증)**을 연결해서 읽습니다.

<!-- classroom-reference:start -->
각 워커가 별도 카운터를 갱신하므로 락이 없지만 코어 수 증가에 따라 처리량이 떨어졌다고 하자. 가상 관측 요약은 “락 대기 없음, 공유 캐시 라인 관련 이벤트 증가”다. 이를 모든 멀티스레드 성능 저하의 원인으로 단정하지 않는다.

먼저 카운터가 메모리에서 가까이 놓였는지 확인한다. **false sharing**은 논리적으로 다른 값이 같은 캐시 라인을 공유해 각 코어의 쓰기가 서로의 라인을 무효화시키는 현상이다. Linux에서 가능한 환경이라면 `perf c2c` 등의 도구를 검토하고, 프로파일로 핫스팟과 캐시 통신을 확인한다.

**수정:** 워커별 값을 적절히 분리하거나 로컬 집계를 한 뒤 덜 자주 합친다. 라인 크기를 무조건 64바이트라고 하드코딩하기보다 대상 플랫폼과 언어의 정렬 기능을 확인한다. padding은 메모리를 늘리고 다른 캐시 문제를 만들 수 있다.

**재검증:** 코어 수별 처리량·p95 지연·메모리 사용량을 같은 작업량으로 측정한다. true sharing이나 NUMA 원격 접근, 메모리 대역폭 포화가 남아 있는지도 확인한다. 값의 원자성 요구는 배치를 바꿔도 사라지지 않는다.

## 판단 근거와 상세 비교

“이 조건에서는 이 방법을 쓰고, 대신 이 부담을 감수한다”라고 설명할 수 있는지 확인해 보세요.

<!-- classroom-reference:start -->
| 선택 | 장점 | 비용 |
|---|---|---|
| 연속 배열 | 순차 접근과 지역성에 유리 | 중간 삽입·크기 변경 비용 |
| 포인터 구조 | 동적 연결을 표현하기 쉬움 | 포인터 추적·분산 할당 |
| 필드별 배열(SoA) | 일부 필드의 일괄 처리·벡터화 | 객체 단위 코드가 복잡해짐 |
| 코어별 로컬 집계 | 경합과 일관성 통신 감소 | 합산 지연과 메모리 증가 |

자료구조의 Big-O가 같아도 CPU가 읽는 바이트 수와 접근 순서에 따라 실제 지연이 달라진다. 데이터 크기가 캐시에 들어가는지, 워킹셋이 다른 요청과 경쟁하는지, NUMA 노드와 할당 위치가 맞는지 확인한다. 더 큰 캐시가 항상 더 빠른 것은 아니며 운영 비용과 워크로드 변화도 비교한다.

CPU 캐시와 Redis 같은 애플리케이션 캐시는 목적이 비슷해 보이지만 무효화와 일관성의 책임이 다르다. 애플리케이션 캐시의 TTL을 바꿔 CPU의 false sharing을 해결할 수는 없다.

**판단 연습:** 초당 수많은 이벤트의 네 필드 중 하나만 집계한다면 AoS와 SoA 중 무엇부터 실험할까? 정확도·집계 지연 허용치, 사용 메모리, 코어별 확장 곡선을 합격 기준으로 정하자.
