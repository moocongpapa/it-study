# 웹 성능 — 사용자가 기다리는 과정을 나눠 줄이기

> **한 문장으로:** 주소 찾기부터 화면 표시와 입력 반응까지 기다리는 위치를 나눠 측정하고 개선합니다.

## 왜 필요한가요?

서버 응답은 빨라도 큰 사진을 받거나 브라우저가 계산하느라 화면이 늦을 수 있습니다. 사용자가 실제로 언제 보고 누를 수 있는지 전체 흐름을 봐야 합니다.

## 일상에서 떠올려 보기

식당에서 주문 접수, 조리, 서빙, 자리 정리까지의 시간을 구분해 보세요. 조리만 빨라져도 서빙이 늦으면 손님은 계속 기다립니다. 웹도 단계별로 가장 지연되는 곳을 찾아야 합니다.

## 순서대로 따라가기

1. 서버 응답과 자료 내려받기, 브라우저 실행·그리기 시간을 구분합니다.
2. 큰 파일·늦게 발견되는 자료·긴 계산 등 주요 원인을 측정합니다.
3. 개선 뒤 실험 환경과 실제 사용자 환경에서 결과와 오류를 함께 확인합니다.

```mermaid
flowchart LR
 A["연결·서버 응답"] --> B["자료 내려받기"] --> C["브라우저 계산"] --> D["화면·입력 반응"]
```

## 작은 예로 확인하기

빠른 컴퓨터와 Wi-Fi에서 한 번 검사한 결과가 느린 휴대폰과 이동통신 사용자를 대표하지 않을 수 있습니다. lab은 통제된 실험, field는 실제 사용자 환경의 관측입니다. 둘을 함께 보면 재현과 실제 영향이 연결됩니다.

## 처음 만나는 용어

| 용어 | 쉬운 뜻 |
|---|---|
| 병목 | 전체 진행을 제한하는 느린 단계입니다. |
| CDN | 사용자 가까운 전달 지점에서 자료를 제공하는 네트워크입니다. |
| lab·field | 조건을 통제한 검사와 실제 사용자 환경의 측정입니다. |
| 렌더링 | 문서와 스타일을 계산해 화면에 표시하는 과정입니다. |

**비유의 한계:** 평가 점수 하나가 모든 사용자 경험을 대표하지 않습니다. 지역·장비·통신·사용 행동이 다르고 빠르게 만들면서 기능이나 접근성을 깨뜨리지 않아야 합니다.

## 스스로 확인

실험 컴퓨터에서 빠르다는 결과만으로 모든 사용자가 빠르다고 할 수 있을까요?

**답과 이유:** 아닙니다. 통제된 lab 검사와 실제 field 관측은 서로 보완합니다. 실제 장비와 네트워크별 분포를 함께 확인해야 합니다.

# 전달량과 실행 비용 줄이기

<!-- beginner-guide:start -->
## 읽기 전 길잡이

이미지 예제에서는 자료를 언제 발견하는지와 차지할 공간을 미리 정했는지 보세요. 파일 전송량과 화면 배치 변화는 서로 다른 개선 대상입니다.

## 이 단계에서 만날 말

| 용어 | 쉬운 뜻 |
|---|---|
| LCP | 화면의 주요 큰 콘텐츠가 표시되는 시점을 보는 지표입니다. |
| INP | 사용자 입력에 화면이 반응하는 지연을 보는 지표입니다. |
| CLS | 예상 밖의 화면 배치 이동을 보는 지표입니다. |
| 코드 분할 | 필요한 코드 묶음을 나눠 받아 실행하는 방식입니다. |
| 개인화 캐시 | 사용자별 자료를 사본으로 저장할 때 구별과 보호가 필요한 캐시입니다. |
| 성능 예산 | 파일 크기·시간 등 허용할 비용을 정한 기준입니다. |

<!-- beginner-guide:end -->

크고 늦게 발견되는 이미지, render-blocking 리소스, 긴 JS 작업을 분해한다. 압축·캐시·CDN·코드 분할은 각각 다른 비용을 줄인다. 브라우저 캐시와 서버 응답 캐시의 개인화 경계를 명시한다.

다음 HTML은 이미지 공간을 미리 확보하는 학습 예제다.

```html
<img src="/hero-800.webp" width="800" height="450"
     alt="학습 경로 지도" fetchpriority="high">
<img src="/below-fold.webp" width="400" height="300"
     alt="다음 학습 카드" loading="lazy">
```

주요 LCP 이미지를 무조건 lazy loading하면 발견과 다운로드가 늦어질 수 있다. 화면 아래 이미지는 lazy loading을 검토한다. preload·높은 우선순위를 모든 리소스에 주면 실제 우선순위가 무너진다. Content-Encoding 압축과 이미지 포맷·해상도는 데이터를 줄이지만 CPU·품질·호환성을 확인한다.

**실습:** DevTools waterfall과 main-thread 작업을 보고 지연이 서버·전달·실행 중 어디에 있는지 분류하자.

# 가상 장애 — CDN 캐시가 사용자 진도를 섞는다

<!-- beginner-guide:start -->
## 읽기 전 길잡이

서버 지표는 괜찮지만 페이지가 느린 상황을 봅니다. 실제 사용자 경로에서 내려받기·긴 JavaScript 작업·배치 계산을 나눠 조사하세요.

<!-- beginner-guide:end -->

가상 개인화 HTML을 공용 캐시로 저장해 다른 사용자에게 보여 주는 문제다. 성능 개선이 보안·정확성을 악화시킬 수 있다. Cache-Control, Vary, 인증 쿠키, edge·브라우저 캐시와 실제 응답을 대조한다.

**수정:** 사용자 데이터 응답은 적절한 private/no-store 계약을 적용하고 공개 콘텐츠는 버전·tag 기반 캐시로 분리한다. 최신성·로그인·권한 경계를 프레임워크 캐시 설정과 맞춘다. 불필요한 DB 조회는 안전한 공개 데이터 캐시로 줄일 수 있다.

**재검증:** 서로 다른 테스트 사용자, cold/warm 캐시, 콘텐츠 변경, 모바일 저성능 기기를 확인한다. field 지표·오류율·데이터 정확성을 함께 측정한다. 한 번의 Lighthouse 결과만으로 운영 전체 성공을 선언하지 않는다.

# 트래픽 증가의 비용과 단계적 최적화

<!-- beginner-guide:start -->
## 읽기 전 길잡이

캐시와 전달량 감소, 서버 계산, 브라우저 계산 중 어디에 비용을 둘지 비교합니다. 사용자별 자료 보호와 비용, 실제 반응 목표를 함께 기준으로 삼으세요.

<!-- beginner-guide:end -->

| 개선 | 기대 이득 | 주의 |
|---|---|---|
| CDN·공개 캐시 | 원본 부하·지역 지연 감소 | 신선도·인가·무효화 |
| 응답·이미지 축소 | 전송·메모리 감소 | 품질·계약 |
| JS 분할·지연 | 초기 실행 비용 감소 | 후속 로딩·실패 UX |
| 서버·DB 개선 | TTFB·처리량 개선 | 앱 렌더링 병목은 별도 |

사용자 흐름별 예산을 정하고 병목 비중이 큰 곳을 먼저 개선한다. 공통 리소스·CDN·DB·CPU의 포화와 캐시 장애 시 원본 용량을 고려한다. 성능 최적화는 정확성·접근성·보안을 만족하며 rollout과 실제 사용자 관측으로 검증한다.

참고: [web.dev Web Vitals](https://web.dev/articles/vitals), [LCP 최적화](https://web.dev/articles/optimize-lcp), [MDN HTTP Caching](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching).
