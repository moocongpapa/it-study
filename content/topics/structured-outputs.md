# 구조화 출력·JSON Schema·의미 검증

> **오늘의 질문** · 칸을 맞춰 쓴 답이면 내용도 반드시 맞을까?

먼저 그림을 눌러 바꿔 볼까요? 답이 달라지는 모습을 천천히 관찰해 보세요.

```learning
{"slug":"structured-outputs","view":"explore"}
```

## 익숙한 장면과 연결해요

주문서 칸을 정해도 수량 칸에 9999를 적은 주문이 실제 가능한지는 따로 확인해야 합니다. 양식과 업무 규칙은 다른 검사입니다.

## 선생님과 한 번 정리해요

AI의 답을 사람이 읽는 데서 그치지 않고 프로그램으로 처리하려면 일정한 형식이 필요합니다. 형식을 맞추는 일과 내용이 맞는지 확인하는 일을 나눠야 잘못된 자동 실행을 줄일 수 있습니다.

**한 줄로 말하면:** 모델 출력을 프로그램이 쓰려면 형식 제약과 파싱뿐 아니라 업무상 값의 의미도 검증해야 합니다.

```learning
{"slug":"structured-outputs","view":"words"}
```

**비유의 한계도 알아둘까요?** 스키마에 맞는 JSON도 거짓 값이나 권한 없는 행동을 포함할 수 있습니다. 제공자별 지원 스키마·거절·중단 응답의 계약도 확인해야 합니다.

```learning
{"slug":"structured-outputs","view":"recall"}
```

```learning
{"slug":"structured-outputs","view":"trace"}
```

## 여기서 연결해 봐요

모델 출력을 프로그램이 쓰려면 형식 제약과 파싱뿐 아니라 업무상 값의 의미도 검증해야 합니다.

왜 이런 순서가 필요한지 말로 설명할 수 있으면 좋아요. 코드와 자세한 설명은 아래에 준비했어요. 낯선 기호는 입력·바뀌는 값·결과로 나눠 읽어 봐요.

<!-- classroom-reference:start -->
## 읽기 전 길잡이

모델 출력을 프로그램이 쓰려면 형식 제약과 파싱뿐 아니라 업무상 값의 의미도 검증해야 합니다. 아래 예제는 외부 시스템에 연결하지 않는 작은 학습용 사례입니다. 입력, 처리 조건, 결과를 순서대로 살펴보세요.

1. 필수 필드·타입·허용 범위로 출력 계약을 정의합니다.
2. 지원되는 구조화 모드로 생성하고 파싱·스키마를 검사합니다.
3. 권한·참조 존재·업무 조건을 서버에서 검증합니다.

## 예제로 확인하기

```python
import json
result=json.loads('{"quantity":2,"sku":"A"}')
stock={"A":3}
assert type(result["quantity"]) is int
assert 0<result["quantity"]<=stock[result["sku"]]
print("형식과 재고 조건 통과")
```

## 결과를 해석하기

작은 서버 검증 예제는 수량 타입과 양수·재고 범위를 검사합니다. 실제 구현은 허용 필드, 키 존재, 사용자 권한과 오류 처리를 포함해야 합니다. 파싱 성공만으로 주문을 실행하지 않습니다.

## 실무에 옮기기 전

스키마에 맞는 JSON도 거짓 값이나 권한 없는 행동을 포함할 수 있습니다. 제공자별 지원 스키마·거절·중단 응답의 계약도 확인해야 합니다. 실제 업무에서는 다운스트림 행동이 중요한 경우 구조화 출력과 서버 의미 검증을 함께 둡니다. 형식 재시도도 횟수·비용을 제한하고 실패 시 안전한 상태를 유지합니다.

**답과 이유:** 정수 형식 검사 뒤 실제 재고 범위를 확인합니다.

# 오늘은 문제를 찾는 탐정이에요

정답을 급하게 고치기 전에 **무엇을 봤는지**와 **왜 그랬을 것 같은지**를 나눠 볼까요? 아래는 학습용 가상·재현 사례예요. 카드를 차례로 눌러 단서를 확인해 보세요.

```learning
{"slug":"structured-outputs","view":"debug"}
```

## 해결 뒤에도 한 번 더

고친 다음 원래 입력으로 다시 확인하는 일을 **재검증**이라고 해요. 한 번 성공한 것만 보고 끝내지 않고, 비슷한 실패 조건에서도 괜찮은지 확인해요.

실제 고객의 장애 기록이 아닌 학습용 재현 시나리오입니다. 결과만 바꾸기 전에 관측한 증거와 원인 가설을 구분합니다.

## 1. 어떤 문제가 생겼나요?

가상 자동 주문이 유효 JSON인데 없는 상품을 참조합니다.

## 2. 먼저 확인할 증거

원본 응답·스키마 통과 결과와 서버 참조 조회를 확인합니다.

## 3. 원인 가설

형식 검증을 업무 검증으로 착각했습니다.

## 4. 수정 방법

상품 존재·재고·권한·중복 실행 조건을 서버에서 검사합니다.

## 5. 재검증

누락 필드·잘못된 키·범위 밖 수량·중단 응답을 회귀 검사합니다.

## 놓치기 쉬운 조건

스키마에 맞는 JSON도 거짓 값이나 권한 없는 행동을 포함할 수 있습니다. 제공자별 지원 스키마·거절·중단 응답의 계약도 확인해야 합니다.

# 이번에는 네가 설계자예요

아래 방법 중 하나를 골라 볼까요? 선택한 방법에서 **얻는 것**과 **감수할 것**을 함께 확인해 보세요. 같은 기술도 상황과 제약이 바뀌면 다른 선택을 할 수 있어요.

```learning
{"slug":"structured-outputs","view":"decide"}
```

## 이유까지 말하면 더 좋아요

“나는 이 방법을 골랐어. 중요한 조건은 이것이고, 대신 이런 부담은 감수할게.”처럼 설명해 보세요. 그러고 나서 조건을 하나 바꾸면 같은 선택을 할지도 생각해 봐요.

<!-- classroom-reference:start -->
## 읽기 전 길잡이

같은 개념도 업무의 규모, 오류 비용, 운영 역량에 따라 적용 방식이 달라집니다. 아래 비교는 특정 제품의 성능 순위가 아닌 선택 기준입니다.

| 선택 | 얻는 점 | 감수할 점 |
|---|---|---|
| 자유 텍스트 파싱 | 유연한 설명 | 깨지기 쉬운 해석 |
| 스키마 제약과 서버 검사 | 계약과 실패 처리 명확 | 스키마 버전·거절 처리 필요 |

## 선택 기준

다운스트림 행동이 중요한 경우 구조화 출력과 서버 의미 검증을 함께 둡니다. 형식 재시도도 횟수·비용을 제한하고 실패 시 안전한 상태를 유지합니다.

## 도입과 운영에서 확인할 것

상품 존재·재고·권한·중복 실행 조건을 서버에서 검사합니다. 누락 필드·잘못된 키·범위 밖 수량·중단 응답을 회귀 검사합니다.
