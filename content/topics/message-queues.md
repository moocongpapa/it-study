# 메시지 큐 — 일을 맡겨 두고 나중에 처리하기

> **한 문장으로:** 요청한 일의 기록을 전달 통로에 남기고 다른 작업자가 자기 속도로 처리하게 합니다.

## 왜 필요한가요?

사용자가 주문할 때 이메일과 영상 변환까지 모두 기다리면 응답이 늦습니다. 일시적으로 많은 일이 들어와도 처리할 작업을 보관하고 나중에 나눠 수행할 수 있어야 합니다.

## 일상에서 떠올려 보기

식당에서 주문표를 전달대에 올리고 주방이 차례로 받아 조리하는 모습을 떠올려 보세요. 안내 직원과 주방은 서로 다른 속도로 일할 수 있습니다. 주문표를 처리했는지 확인하는 기록도 필요합니다.

## 순서대로 따라가기

1. 보내는 쪽이 처리할 일의 내용과 식별자를 메시지로 남깁니다.
2. 받는 작업자가 메시지를 읽고 업무를 수행합니다.
3. 완료를 확인하고 실패 시 다시 처리하는 규칙을 사용합니다. 같은 메시지가 다시 올 가능성도 다룹니다.

```mermaid
flowchart LR
 A["주문 서비스"] --> B["처리할 일 보관"] --> C["메일 작업자"] --> D["완료 확인"]
```

## 작은 예로 확인하기

작업자가 이메일을 보낸 직후 완료 표시 전에 멈추면 시스템은 일을 다시 전달할 수 있습니다. ‘적어도 한 번’ 전달은 중복 가능성을 포함합니다. 메시지 ID나 업무의 고유 기준으로 이미 처리했는지 확인하는 설계가 필요합니다.

## 처음 만나는 용어

| 용어 | 쉬운 뜻 |
|---|---|
| 메시지 | 처리할 일이나 발생한 사건을 담은 데이터입니다. |
| 생산자·소비자 | 메시지를 보내는 쪽과 읽어 처리하는 쪽입니다. |
| 큐 | 처리를 기다리는 메시지를 관리하는 통로입니다. |
| ACK | 메시지를 처리했다는 확인입니다. |

**비유의 한계:** 주문표 전달은 모든 메시지 제품의 순서와 저장 보장을 설명하지 못합니다. 큐를 넣어도 일의 양이 처리 능력을 계속 넘으면 대기가 쌓입니다.

## 스스로 확인

at-least-once 전달이면 같은 메시지를 두 번 처리할 가능성을 무시해도 될까요?

**답과 이유:** 안 됩니다. 재전달로 중복이 생길 수 있습니다. 처리 결과와 고유 업무 기준을 기록해 중복 효과를 막아야 합니다.
<!-- level:2 -->
# 처리 완료와 확인의 순서

<!-- beginner-guide:start -->
## 읽기 전 길잡이

교육용 코드에서 이미 처리한 ID를 확인하는 부분을 보세요. 실제 업무 변경과 처리 기록을 같은 안전한 저장 경계에 두어야 중간 실패를 다룰 수 있다는 점에 집중하세요.

## 이 단계에서 만날 말

| 용어 | 쉬운 뜻 |
|---|---|
| offset | 로그형 통로에서 메시지 위치를 나타내는 값입니다. |
| at-least-once | 유실을 줄이기 위해 재전달을 허용하는 보장으로 중복을 고려해야 합니다. |
| 멱등 처리 | 같은 일을 다시 받아도 업무 효과를 중복시키지 않는 처리입니다. |
| 백프레셔 | 받는 쪽의 처리 용량에 맞춰 유입을 조절하는 것입니다. |
| dead-letter queue | 반복 실패한 메시지를 별도로 모아 조사·복구하는 통로입니다. |
| outbox | 업무 데이터 변경과 보낼 사건 기록을 같은 로컬 저장 경계에 두는 방식입니다. |

<!-- beginner-guide:end -->

소비자는 메시지를 읽고 업무 상태를 변경한 뒤 ACK 또는 offset commit을 한다. 상태 변경 후 확인 전에 죽으면 다시 전달돼 중복이 생길 수 있다. 먼저 확인하고 업무를 하면 장애 때 누락될 수 있다. 외부 효과와 확인의 경계가 핵심이다.

Python 3의 **교육용 멱등 소비자 모델**이다. 실제 DB에는 같은 트랜잭션과 unique 제약으로 구현해야 한다.

```python
processed, total = set(), 0
def consume(event_id, amount):
    global total
    if event_id in processed: return
    total += amount
    processed.add(event_id)
consume("e-1", 10); consume("e-1", 10)
assert total == 10
```

메모리 set만으로 프로세스 재시작이나 여러 워커의 경쟁을 막을 수 없다. durable event ID와 업무 저장을 연결한다. 순서 보장은 Kafka에서 일반적으로 파티션 단위이며 전역 순서가 아니다. 큐에서 여러 소비자의 완료 순서도 전달 순서와 다를 수 있다.

# 가상 장애 — 독성 메시지 재시도가 큐를 막는다

<!-- beginner-guide:start -->
## 읽기 전 길잡이

처리 후 확인 전에 멈추는 경우와 확인 후 처리 전에 멈추는 경우를 각각 따라가 봅니다. 중복과 누락이 생기는 경계가 달라지므로 사건 순서를 기록해야 합니다.

<!-- beginner-guide:end -->

가상 소비자가 잘못된 스키마 메시지를 무한 재시도해 처리량을 소모한다. transient 오류와 영구 입력 오류를 구분하고 재시도 횟수·처리 시간·lag·DLQ 원인을 본다.

**수정:** 기한·지수 backoff·지터·재시도 상한을 두고 영구 실패를 quarantine/DLQ에 보낸다. DLQ는 폐기함이 아니라 원인·수정·재처리 절차가 필요한 운영 큐다. 메시지 스키마 버전과 호환성을 검증한다.

**재검증:** 처리 후 ACK 전 장애, 중복, 순서 변경, poison payload, 재처리에서 업무 결과가 한 번의 의미를 유지하는지 확인한다. backlog가 감소할 여유 처리량과 복구 시간도 측정한다.

# 전달 보장과 용량 계약

<!-- beginner-guide:start -->
## 읽기 전 길잡이

즉시 끝내야 하는 일과 나중에 처리해도 되는 일을 구분합니다. 대기 시간, 순서 보장, 재처리, 운영 복구 비용을 기준으로 통로와 소비 방식을 비교하세요.

<!-- beginner-guide:end -->

| 선택 | 장점 | 비용 |
|---|---|---|
| 작업 큐 | 작업 분배와 확인 | 중복·재시도·가시성 |
| 보관 로그 | 재읽기·여러 소비자 | 파티션·보존·offset 운영 |
| 동기 호출 | 즉시 결과 계약 | 의존 지연·실패 전파 |

업무 DB 변경과 메시지 발행의 dual-write를 피하려면 outbox나 CDC를 검토한다. 메시지를 보냈지만 DB rollback되거나 반대 상황을 다룬다. 큐 저장량과 소비 속도, 최대 이벤트 크기, retention, replay 부하를 계획한다. 전달 보장·업무 멱등성·사용자 확인을 각각 명시한다.
