# OSI 7계층과 캡슐화

> **먼저 한 문장:** 네트워크는 메시지의 뜻, 주소, 전달 방식 같은 책임을 여러 단계로 나누어 처리합니다.

동영상·메일·쇼핑 앱이 서로 다른 일을 해도 같은 인터넷을 이용합니다. 각 앱이 모든 전기 신호와 전달 경로를 직접 구현하지 않도록 책임을 나누는 관점이 필요합니다.

## 먼저 알아둘 말

```learning
{"slug":"osi-encapsulation","view":"words"}
```

## 작은 예로 이해하기

한 건물 주소에 여러 가게가 있을 수 있습니다. IP 주소가 컴퓨터의 네트워크 위치를 찾는 데 쓰인다면, 포트 번호는 그 안의 통신 대상을 구분하는 데 쓰입니다. 같은 IP에서도 웹 서비스와 다른 서비스가 서로 다른 포트를 사용할 수 있습니다.

## 익숙한 장면과 연결하기

선물의 내용, 택배 상자, 받는 주소, 운송 경로를 구분해 보세요. 내용이 바뀌어도 택배회사의 운송 방법을 매번 다시 만들 필요는 없습니다. 데이터를 보내는 쪽은 필요한 정보를 덧붙이고 받는 쪽은 그 정보를 해석해 안의 내용을 꺼냅니다.

**비유의 한계 — 이 점은 달라요:** 실제 인터넷 구현이 OSI의 일곱 칸과 항상 정확히 나뉘지는 않습니다. 포장 상자 비유는 책임을 구분하는 데 유용하지만 모든 단계가 물리적 상자를 추가한다는 뜻은 아닙니다.

## 직접 확인하기

메시지 → 주소·전달 정보 → 신호로 보내기 순서로 읽어 보세요. 뒤의 과정에서 필요한 것이 앞에서 어떻게 준비되는지 찾습니다. 숫자는 읽는 순서이며 모든 상황이 정확히 세 단계라는 뜻은 아닙니다.

# OSI 7계층과 캡슐화 · 작동 원리

앱 메시지에서 실제 전송 구간까지 한 요청을 내려가며 읽어 보세요. 아래 명령은 자신의 네트워크 인터페이스와 경로 정보를 관찰합니다. 메시지 내용, IP 주소, 현재 연결 구간을 분리하는 것이 목적입니다.

## 전체 흐름부터 보기

```learning
{"slug":"osi-encapsulation","view":"trace"}
```

## 예제와 내부 동작

아래 자료를 읽을 때 **입력 → 바뀌는 값이나 상태 → 결과**를 찾아보세요. 모르는 말은 밑줄 표시를 눌러 뜻을 확인할 수 있어요.

<!-- classroom-reference:start -->
앱은 HTTP 메시지를 만들고, HTTPS라면 TLS가 보호하며, TCP 또는 QUIC 같은 전송이 바이트·스트림 전달을 관리한다. IP 계층은 목적지까지 패킷을 라우팅한다. Ethernet이나 Wi-Fi 링크는 현재 구간에서 프레임을 전달한다. 경로 중 NAT가 주소와 포트를 변환할 수 있어 앱에서 본 끝점과 외부 패킷의 끝점이 다를 수 있다.

학습용 Linux 명령이다. 인터넷 요청 없이 현재 호스트의 인터페이스와 경로를 확인한다.

```bash
ip addr show
ip route show
ss -lnt
```

`ip addr`는 인터페이스 주소, `ip route`는 다음 홉 선택, `ss -lnt`는 TCP 리스닝 끝점을 보여 준다. 실제 패킷 캡처에서는 관측 인터페이스와 방향을 명시한다. MTU는 링크에서 전송 가능한 크기 제약과 관련되고, 상위 메시지 크기와 같지 않다. 헤더가 늘면 실제 페이로드 예산이 줄 수 있다.

**실습:** 같은 호스트에 두 포트를 리스닝시켜 IP는 같지만 서비스가 구분되는 것을 확인하자. MAC 주소만으로 다른 네트워크의 호스트를 찾는다고 설명하지 않는다.

# OSI 7계층과 캡슐화 · 문제 해결

통신 실패를 조사할 때 주소를 못 찾는지, 연결을 못 만드는지, 앱 응답이 잘못됐는지 단계별로 나눕니다. 한 단계의 성공이 전체 요청 성공을 뜻하지는 않습니다.

## 구체적인 사례와 확인 방법

같은 증상에도 원인이 여럿일 수 있어요. 먼저 발생 조건을 기록하고 증상을 재현할 수 있는지 확인하세요. **관찰한 증상 → 확인할 자료 → 수정 → 수정 후 확인(같은 조건으로 재검증)**을 연결해서 읽습니다.

<!-- classroom-reference:start -->
가상 서비스에서 ICMP 응답은 있지만 HTTPS 연결이 실패한다. IP 도달 가능성만으로 포트·전송·TLS·앱의 정상 상태를 증명할 수 없다. 한 계층의 성공을 전체 시스템 성공으로 확대하지 않는다.

진단 순서를 이름 해석 → 목적지 경로 → TCP 연결 → TLS 협상 → HTTP 응답으로 나눈다. `curl -v --connect-timeout 3 https://example.com`은 연결과 프로토콜 단계의 단서를 제공한다. 실제 서비스에서는 대상과 테스트 권한을 확인하고 토큰이 출력되는 로그를 공유하지 않는다.

**가설 검증:** TCP 연결 거부면 리스너·포트·방화벽을, 타임아웃이면 경로와 필터링을, 인증서 오류면 호스트명·체인·유효기간을 조사한다. IPv4/IPv6 차이와 프록시 환경변수도 확인한다.

**재검증:** 장애가 난 계층의 단위 검사와 사용자 요청 전체 검사를 모두 수행한다. 앱 헬스체크가 살아도 외부 경로가 실패할 수 있어 외부 관측이 필요하다.

# OSI 7계층과 캡슐화 · 실무 선택

계층을 나누면 특정 부분을 바꾸고 문제를 조사하기 쉬워집니다. 여러 중간 장치를 추가할 때는 각 장치가 어느 정보를 읽고 바꾸는지, 어디에서 암호화가 끝나는지 확인하세요.

## 판단 근거와 상세 비교

“이 조건에서는 이 방법을 쓰고, 대신 이 부담을 감수한다”라고 설명할 수 있는지 확인해 보세요.

<!-- classroom-reference:start -->
| 관측 | 답할 수 있는 질문 | 한계 |
|---|---|---|
| 링크·라우팅 상태 | 패킷이 어디로 나가는가 | 앱 응답 보장 아님 |
| 전송 연결 검사 | 포트에 연결할 수 있는가 | 업무 성공 보장 아님 |
| TLS 검사 | 상대와 암호화 계약이 맞는가 | 데이터 정확성 보장 아님 |
| 앱 합성 테스트 | 사용자 흐름이 동작하는가 | 내부 원인 구분 필요 |

큰 시스템에서는 프록시·서비스 메시·터널 등 여러 캡슐화와 끝점이 생긴다. 어느 지점에서 TLS가 종료되고 어떤 주소가 로그에 남는지 문서화한다. 오버레이 MTU와 방화벽 정책을 개별 팀이 다르게 가정하면 특정 크기 패킷만 실패하는 문제가 생긴다.

**판단 연습:** 외부 로드밸런서에서는 성공, Pod에서는 정상, 사용자만 실패한다면 어떤 관측 위치가 빠졌을까? 계층별 검사 결과와 종단 요청을 연결해 장애를 설명하자.

참고: [RFC 1122 — Internet Host Requirements](https://www.rfc-editor.org/rfc/rfc1122), [Linux ip](https://man7.org/linux/man-pages/man8/ip.8.html).
