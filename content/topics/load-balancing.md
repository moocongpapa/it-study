# 로드 밸런싱과 리버스 프록시

> **먼저 한 문장:** 사용자의 요청을 여러 서버에 나누고, 일을 받을 준비가 된 서버로 보내는 방법입니다.

서버 하나에 요청이 몰리면 느려지거나 멈출 수 있습니다. 서버를 여러 대 둔 뒤 어떤 서버로 요청을 보낼지 정하는 역할이 필요합니다.

## 먼저 알아둘 말

```learning
{"slug":"load-balancing","view":"words"}
```

## 작은 예로 이해하기

사진 요청은 사진 서버로, 주문 요청은 주문 서버로 보내고 싶다면 요청의 내용 일부를 읽어야 합니다. L7 방식은 HTTP 경로와 헤더 같은 정보를 사용할 수 있습니다. 단순히 연결 정보를 보고 나누는 L4 방식과 판단 재료가 다릅니다.

## 익숙한 장면과 연결하기

은행 안내 직원이 손님을 여러 창구로 보낸다고 생각해 보세요. 쉬는 창구에는 보내지 않고, 창구의 처리 속도와 기다리는 줄도 고려합니다. 손님은 안내 데스크만 알면 되고 실제 일을 맡는 창구가 여러 개일 수 있습니다.

**비유의 한계 — 이 점은 달라요:** 창구 수를 늘려도 공용 데이터베이스가 느리면 전체 속도가 제한됩니다. 살아 있는 서버가 일을 받을 준비까지 됐다고 볼 수 없고, 중간 장치의 실패도 고려해야 합니다.

## 직접 확인하기

들어오는 양과 처리하는 양을 다르게 설정한 뒤 한 차례 진행하세요. 처리하지 못한 요청이 대기열에 남는지 확인합니다. 실제 시스템의 시간을 예측하는 측정 도구는 아닙니다.

# 로드 밸런싱과 리버스 프록시 · 작동 원리

NGINX 설정에서 요청을 받는 부분과 실제 서버 목록을 찾으세요. 먼저 두 서버가 준비됐다는 전제와 검사·종료 절차를 이해한 뒤 설정 값을 읽으면 됩니다.

## 전체 흐름부터 보기

```learning
{"slug":"load-balancing","view":"trace"}
```

## 예제와 내부 동작

아래 자료를 읽을 때 **입력 → 바뀌는 값이나 상태 → 결과**를 찾아보세요. 모르는 말은 밑줄 표시를 눌러 뜻을 확인할 수 있어요.

<!-- classroom-reference:start -->
헬스체크는 서버를 대상에 포함할지 판단한다. 포트 응답, 프로세스 생존, 업무 준비 상태는 다르다. readiness와 liveness를 나누고 검사 간격·실패 횟수·회복 조건을 정한다. 종료하는 서버는 새 요청을 멈추고 기존 요청을 drain할 시간이 필요하다.

다음은 NGINX 설정 예시이며 실행에는 로컬 backend 두 개와 NGINX 설치가 필요하다.

```nginx
upstream app_pool {
    server 127.0.0.1:3001;
    server 127.0.0.1:3002;
}
server {
    listen 8080;
    location / {
        proxy_pass http://app_pool;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_connect_timeout 2s;
        proxy_read_timeout 10s;
    }
}
```

이 최소 설정에는 운영용 능동 헬스체크·TLS·인증·접근 로그 정책이 모두 포함된 것은 아니다. upstream 제품·에디션의 지원 기능을 확인한다. 프록시가 넣는 전달 헤더는 신뢰할 프록시 경계에서만 사용해야 하며 클라이언트가 보낸 값을 그대로 인증 판단에 쓰지 않는다.

# 로드 밸런싱과 리버스 프록시 · 문제 해결

서버를 교체한 순간 요청이 실패하는 가상 상황을 봅니다. 새 서버가 준비되기 전에 요청을 받았는지, 빠지는 서버의 기존 요청을 끝낼 시간이 있었는지 확인하세요.

## 구체적인 사례와 확인 방법

같은 증상에도 원인이 여럿일 수 있어요. 먼저 발생 조건을 기록하고 증상을 재현할 수 있는지 확인하세요. **관찰한 증상 → 확인할 자료 → 수정 → 수정 후 확인(같은 조건으로 재검증)**을 연결해서 읽습니다.

<!-- classroom-reference:start -->
가상 서버 교체 과정에서 로드밸런서는 아직 종료 중인 서버로 요청을 보낸다. 다음처럼 프록시와 backend 로그를 연결한다.

```text
proxy: upstream connection closed before response
backend: shutting down, active_requests=7
```

먼저 실패가 연결 설정, 응답 대기, 앱 오류 중 어느 단계인지 나눈다. 요청 ID로 양쪽 로그를 맞추고 대상 상태·drain 기간·readiness 전환 시점을 확인한다. 헬스체크가 성공해도 특정 경로가 실패할 수 있다.

**수정:** 새 요청을 차단한 뒤 진행 요청을 제한 시간 안에 마무리하고 종료한다. 프록시·앱·오케스트레이터의 기한을 서로 맞춘다. 상태 변경 요청의 자동 재시도는 업무 중복을 일으킬 수 있어 멱등성을 검토한다.

**재검증:** 부하를 유지하며 rolling 배포, 강제 장애, 느린 요청을 재현한다. 502·504·중복 처리·연결 실패율과 p95 지연을 확인한다.

# 로드 밸런싱과 리버스 프록시 · 실무 선택

요청 내용으로 세밀하게 나눌수록 기능과 관측이 늘지만 처리 비용도 생깁니다. 연결 규모, 보안 경계, 장애 복구를 함께 비교해 앞단 구조를 정하세요.

## 선택지를 비교해 보기

방법을 하나 고르면 이득과 부담을 함께 볼 수 있어요. 어떤 조건을 중요하게 보는지에 따라 선택이 달라집니다.

```learning
{"slug":"load-balancing","view":"decide"}
```

## 판단 근거와 상세 비교

“이 조건에서는 이 방법을 쓰고, 대신 이 부담을 감수한다”라고 설명할 수 있는지 확인해 보세요.

<!-- classroom-reference:start -->
| 선택 | 이득 | 비용 |
|---|---|---|
| L4 | 상대적으로 단순한 전송 분산 | 앱 경로별 정책 제한 |
| L7 | 경로·헤더별 라우팅과 관측 | TLS·파싱·정책 운영 비용 |
| sticky session | 서버 로컬 상태 유지가 쉬움 | 장애·불균형·이관 문제 |
| 외부 세션 저장 | 서버 교체와 수평 확장 용이 | 저장소 의존·지연·일관성 |

대규모 트래픽에서는 유입을 고르게 나누는 것뿐 아니라 과부하 서버에 더 보내지 않는 것이 중요하다. 큐 길이·동시 처리·비용이 큰 요청의 분포를 본다. 모든 backend가 공유하는 DB가 병목이면 서버 증설만으로 처리량이 늘지 않는다.

**판단 연습:** 장기 WebSocket 연결과 짧은 HTTP 요청을 같은 분산 정책으로 처리해야 할까? 연결 이동·drain·지역 장애·사용자 상태 요구를 근거로 정책을 정하고 backend별 부하 편차를 관측하자.

참고: [NGINX HTTP Load Balancing](https://docs.nginx.com/nginx/admin-guide/load-balancer/http-load-balancer/), [Kubernetes Pod 종료](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/).
