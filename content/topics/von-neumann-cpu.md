# 폰 노이만 구조와 CPU 레지스터

> **먼저 한 문장:** CPU는 메모리에서 명령을 가져와 해석하고, 작은 작업 공간에서 계산한 뒤 결과를 저장합니다.

컴퓨터가 계산·사진 편집·게임처럼 서로 다른 일을 하려면 명령을 바꿔 실행할 수 있어야 합니다. 폰 노이만 구조는 명령과 데이터를 메모리에 저장해 사용하는 기본 관점입니다.

## 작은 예로 이해하기

‘3을 준비한다 → 2를 더한다 → 결과를 저장한다’는 명령을 차례로 실행하면 5가 남습니다. 중간 계산값을 가까운 작은 공간에 두면 큰 메모리에서 매번 다시 가져올 필요를 줄일 수 있습니다.

## 익숙한 장면과 연결하기

요리사가 조리법을 읽고 재료를 꺼내 요리한다고 생각해 보세요. CPU는 요리사, 메모리는 조리법과 재료를 두는 공간, 레지스터는 손에 들고 바로 쓰는 작은 그릇과 비슷합니다. 어디까지 읽었는지 표시한 책갈피는 프로그램 카운터에 해당합니다.

**비유의 한계 — 이 점은 달라요:** 현대 CPU는 여러 명령의 처리를 겹치고 실행 순서를 조정하기도 합니다. 요리사 한 명이 반드시 하나씩 끝낸다는 비유로 전체 내부 동작을 설명할 수는 없습니다.

# 폰 노이만 구조와 CPU 레지스터 · 작동 원리

교육용 CPU 모델이 명령 하나를 실행할 때 값을 어떻게 바꾸는지 봅니다. 실제 칩 전체를 재현하는 코드는 아닙니다. PC, 입력값, 계산 결과를 한 줄씩 추적하면 실행 흐름을 이해할 수 있습니다.

## 전체 흐름부터 보기

```learning
{"slug":"von-neumann-cpu","view":"trace"}
```

## 예제와 내부 동작

아래 자료를 읽을 때 **입력 → 바뀌는 값이나 상태 → 결과**를 찾아보세요. 모르는 말은 밑줄 표시를 눌러 뜻을 확인할 수 있어요.

<!-- classroom-reference:start -->
명령 집합(ISA)은 프로그램에 보이는 연산·레지스터·주소 규칙의 계약이다. CPU 구현은 같은 ISA를 다양한 파이프라인·캐시·실행 장치로 실현할 수 있다. 기본 흐름은 PC로 명령 주소 선택 → 명령 해독 → 피연산자 읽기 → 연산 → 결과 기록 → 다음 PC 결정이다.

아래 Python 3 코드는 실제 CPU 에뮬레이터의 전체 구현이 아닌 **교육용 명령 모델**이다. 실행 가능하며 상태 전이를 눈으로 볼 수 있다.

```python
program = [("LOAD", 5), ("ADD", 3), ("STORE", 0), ("HALT", 0)]
pc, acc, memory = 0, 0, [0]
while True:
    op, arg = program[pc]
    print("pc", pc, "acc", acc, "op", op)
    pc += 1
    if op == "LOAD": acc = arg
    elif op == "ADD": acc += arg
    elif op == "STORE": memory[arg] = acc
    elif op == "HALT": break
print(memory)  # [8]
```

여기서 `acc`는 작업 레지스터, `pc`는 다음 명령의 인덱스다. 실제 CPU는 주소가 바이트 단위인지, 명령 길이가 고정인지 등 ISA에 따른 차이가 있다. 명령 실행에 메모리 접근이 필요한 경우 캐시와 주소 변환을 거친다. 파이프라인에서는 여러 명령이 서로 다른 단계에 있으며 데이터 의존성, 분기 예측 실패, 캐시 미스가 진행을 지연시킨다.

**실습:** ADD 앞에 LOAD를 제거해 결과가 바뀌는 이유를 설명하자. 그다음 분기 명령을 추가해 PC가 항상 한 칸씩만 증가하지 않도록 모델을 확장해 보자.

# 폰 노이만 구조와 CPU 레지스터 · 문제 해결

CPU 성능 문제를 조사할 때는 계산할 일이 많은지, 데이터를 기다리는지 구분합니다. 명령 수·메모리 대기·분기 실패처럼 서로 다른 원인이 같은 ‘느리다’는 증상을 만들 수 있습니다.

## 구체적인 사례와 확인 방법

같은 증상에도 원인이 여럿일 수 있어요. 먼저 발생 조건을 기록하고 증상을 재현할 수 있는지 확인하세요. **관찰한 증상 → 확인할 자료 → 수정 → 수정 후 확인(같은 조건으로 재검증)**을 연결해서 읽습니다.

<!-- classroom-reference:start -->
가상 서비스에서 CPU 사용률은 높지만 처리량이 낮다. “클럭을 높이면 된다”는 결론 전에 어떤 명령과 대기가 시간을 쓰는지 확인해야 한다.

```text
sample: cycles high / instructions lower than baseline
sample: cache-misses increased / branch-misses increased
```

이것은 설명용 관측 요약이며 실제 성능 수치가 아니다. Linux 학습 환경에서 `perf stat -- ./program`으로 cycles, instructions, branch/cache 관련 이벤트를 볼 수 있다. 이벤트 지원과 권한은 CPU·커널·환경마다 다르다. CPI나 IPC는 단독 합격 기준이 아니며 동일 작업량과 빌드 조건에서 비교해야 한다.

프로파일에서 뜨거운 함수를 찾고, 객체 포인터를 따라가는 접근인지, 예측하기 어려운 분기가 많은지, 실제로 반복 연산이 불필요한지 가설을 세운다. 컴파일러 최적화가 측정 루프를 제거하지 않도록 결과를 사용한다. JIT 워밍업과 CPU 주파수 변동도 기록한다.

**수정과 재검증:** 알고리즘·자료 배치·불필요한 분기 중 하나만 바꾸고 동일 입력으로 처리량·p95 지연·CPU 시간을 다시 측정한다. 명령 수 감소가 전체 응답 시간 개선으로 연결되는지 확인하고, CPU가 아닌 DB 대기를 함께 제외한다.

더 빠른 CPU를 고르는 일은 숫자 하나를 비교하는 것보다 복잡합니다. 작업이 얼마나 동시에 실행되는지와 데이터를 얼마나 빨리 공급할 수 있는지 함께 비교해 보세요.

<!-- classroom-reference:start -->
| 선택 | 장점 | 확인할 비용 |
|---|---|---|
| 범용 CPU | 분기 많은 작업과 운영 생태계에 유리 | 메모리 병목·직렬 구간 |
| SIMD 벡터화 | 독립된 동일 연산을 묶어 처리 | 정렬·분기·데이터 배치 제약 |
| GPU 등 가속기 | 병렬 계산을 대량 처리 | 전송·배치·메모리·운영 비용 |

CPU를 고를 때 코어 수와 클럭만 비교하지 않는다. 단일 요청의 직렬 경로, 동시성, 메모리 대역폭, 캐시 크기, ISA 지원, 라이선스 비용을 실제 워크로드로 측정한다. 코어 수가 두 배여도 순차 구간과 공유 락 때문에 처리량이 같은 비율로 늘지 않는다.

프로그램의 이식성은 ISA와 ABI, 런타임 및 네이티브 의존성에 영향을 받는다. 컨테이너가 다른 CPU 아키텍처의 바이너리를 자동으로 네이티브 실행해 주는 것은 아니다. 에뮬레이션·다중 아키텍처 빌드 비용을 계획한다. 사용자 입력을 기계 명령처럼 취급하는 실행 기능에는 별도 격리가 필요하다.
