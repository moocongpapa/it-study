# 스택·힙·GC — 작업 메모를 쓰고 필요 없는 자료 정리하기

> **한 문장으로:** 프로그램은 실행 기록과 객체를 메모리에 보관하고, 더는 필요 없는 공간을 다시 사용할 수 있게 정리합니다.

## 왜 필요한가요?

함수가 다른 함수를 부르고 여러 객체를 만들 때 진행 상태와 데이터 수명을 관리해야 합니다. 정리되지 않는 데이터가 계속 쌓이면 메모리가 부족해질 수 있습니다.

## 일상에서 떠올려 보기

스택은 일을 잠깐 맡기고 돌아올 순서를 적은 메모 더미, 힙은 여러 작업이 참조하는 공용 자료 보관실로 생각해 보세요. GC는 현재 업무에서 찾아갈 수 없는 자료를 찾아 정리하는 관리인과 비슷합니다.

## 순서대로 따라가기

1. 함수가 호출되면 돌아갈 위치와 필요한 실행 기록이 스택에 쌓입니다.
2. 실행 환경의 규칙에 따라 객체를 만들고 다른 코드가 그 객체를 참조합니다.
3. GC가 있는 환경은 시작 참조에서 더 이상 찾아갈 수 없는 객체를 회수 대상으로 판단합니다.

```mermaid
flowchart LR
 A["실행 중 참조"] --> B["찾아갈 수 있는 객체: 유지"]
 C["참조 경로 없음"] --> D["GC 회수 대상"]
```

## 작은 예로 확인하기

오래된 주문 자료를 더 쓰지 않기로 했는데 전역 목록에 계속 남겨 두면 앱에서 그 자료를 찾아갈 수 있습니다. GC는 ‘개발자가 안 쓰고 싶다’는 의도를 읽지 못합니다. 불필요한 참조를 정리해야 회수 대상으로 바뀔 수 있습니다.

## 처음 만나는 용어

| 용어 | 쉬운 뜻 |
|---|---|
| 스택 | 함수 호출의 진행과 복귀를 위한 기록을 쌓는 공간입니다. |
| 힙 | 실행 중 만들어진 객체 등을 보관하는 메모리 공간입니다. |
| 참조 | 어떤 데이터나 객체를 가리키는 연결입니다. |
| GC | 객체의 사용 가능 상태를 추적해 메모리를 회수하는 기능입니다. |

**비유의 한계:** 객체가 어디에 놓이는지는 언어와 구현에 따라 달라집니다. ‘지역 변수는 모두 스택’처럼 단정할 수 없습니다. GC가 있어도 파일·연결 같은 외부 자원의 정리 책임까지 모두 없어지지는 않습니다.

## 스스로 확인

자료를 더 쓰지 않지만 앱의 목록에서 계속 가리키고 있습니다. GC는 이를 바로 회수할까요?

**답과 이유:** 추적 GC에서는 루트에서 그 자료에 도달할 수 있다면 살아 있는 대상으로 봅니다. 불필요한 참조가 남았는지 확인해야 합니다.
<!-- level:2 -->
# 객체 생존과 회수 전략

<!-- beginner-guide:start -->
## 읽기 전 길잡이

예제에서는 객체들이 서로 가리키는 관계와 참조를 제거한 뒤의 상태를 봅니다. GC 실행 횟수 자체보다 어느 시작점에서 어떤 객체에 도달할 수 있는지 따라가세요.

## 이 단계에서 만날 말

| 용어 | 쉬운 뜻 |
|---|---|
| 루트 | GC가 살아 있는 객체를 찾기 시작하는 참조 지점입니다. |
| 참조 카운팅 | 객체를 가리키는 참조의 수로 수명을 관리하는 방식입니다. |
| 순환 참조 | 객체들이 서로를 가리키며 고리를 이루는 상태입니다. |
| 세대 수집 | 객체의 수명 특성에 따라 묶음을 나누어 회수하는 방식입니다. |
| 런타임 | 프로그램 실행과 메모리 관리 등을 제공하는 실행 환경입니다. |
| 메모리 누수 | 필요 없어도 계속 유지되거나 회수되지 않는 메모리가 쌓이는 문제입니다. |

<!-- beginner-guide:end -->

추적 GC는 루트에서 연결을 따라 살아 있는 객체를 찾는다. 참조 카운팅은 참조 수로 수명을 관리하지만 순환 참조에는 추가 대응이 필요하다. 실제 런타임은 여러 기법을 섞고 세대·이동·동시 수집 등의 특성이 다르다.

Python 3의 순환 참조 관찰 예제다. 상세 수집 횟수는 버전에 따라 달라질 수 있다.

```python
import gc, weakref
class Item: pass
a, b = Item(), Item()
a.other, b.other = b, a
ref = weakref.ref(a)
del a, b
gc.collect()
assert ref() is None
```

스택 프레임에는 호출 상태와 참조가 있을 수 있고 참조의 대상은 별도의 객체일 수 있다. 언어의 escape analysis가 객체 배치를 바꾸기도 한다. C/C++에서는 할당·해제와 포인터 수명을, Rust에서는 소유권·차용 계약을, GC 언어에서는 루트 경로와 수집 비용을 이해해야 한다.

**실습:** 외부 리스트에 참조를 보관한 경우와 보관하지 않은 경우를 비교하자. 메모리 회수와 OS에 메모리를 즉시 반환하는 것도 같은 보장은 아니다.

# 가상 장애 — GC 후에도 힙이 줄지 않는다

<!-- beginner-guide:start -->
## 읽기 전 길잡이

메모리가 계속 늘면 단순히 GC가 느리다고 판단하지 않고 누가 객체를 붙잡고 있는지 확인합니다. 캐시·전역 목록·이벤트 구독이 오래된 자료를 유지하는지 조사해 보세요.

<!-- beginner-guide:end -->

가상 서버가 완료한 요청의 객체를 전역 추적 리스트에 계속 남긴다. GC 실행 횟수를 늘려도 그 객체는 도달 가능해 회수되지 않는다. 먼저 live heap, 할당률, RSS와 수집 후 객체 수를 구분한다.

**진단:** 힙 스냅샷에서 객체를 붙잡는 루트 경로를 확인하고 캐시·리스너·클로저·주기 작업이 수명을 늘리는지 본다. RSS만 보고 객체 누수라고 단정하지 않는다. allocator 예약 공간이나 파일 매핑도 영향을 준다.

**수정:** 캐시 크기·TTL·삭제 정책과 구독 해제를 명시한다. 객체를 무조건 풀링하면 살아 있는 메모리가 오히려 늘 수 있어 근거를 측정한다. 파일·소켓은 context manager나 명시적 close로 정리한다.

**재검증:** 요청 수를 반복 증가시켜 수집 후 생존 객체와 메모리가 일정 범위로 안정되는지 확인한다. GC pause 분포와 처리량을 함께 비교한다.

# 수명 관리 전략의 트레이드오프

<!-- beginner-guide:start -->
## 읽기 전 길잡이

회수 작업은 메모리를 되찾지만 실행 중 지연과 CPU 비용을 만들 수 있습니다. 객체를 적게 만들지, 오래 유지할지, 다른 관리 방식을 쓸지 실제 부하로 비교하세요.

<!-- beginner-guide:end -->

| 방식 | 강점 | 책임 |
|---|---|---|
| GC | 많은 객체 수명 관리 자동화 | 도달성 누수·pause·힙 예산 |
| 참조 카운팅 | 해제 시점 예측에 유리한 경우 | 순환·카운트 비용 |
| 소유권/RAII | 명시적인 수명과 자원 정리 | API 설계·소유권 복잡성 |
| 수동 할당 | 세밀한 제어 | 누수·이중 해제·use-after-free |

대규모 서버는 힙 최대값만 조정하지 않는다. 객체 할당률, 장수 객체 비율, 요청 동시성, 외부 자원을 포함한 메모리 예산을 정한다. pause 목표가 빡빡하면 런타임 수집기·데이터 구조·할당 패턴을 함께 비교한다.

**판단 연습:** 수명이 짧은 요청 객체 수백만 개와 장수 캐시를 같은 정책으로 관리할까? 수집 후 live set, p99 pause, RSS, 처리량을 선택 기준으로 삼자.

참고: [Python gc](https://docs.python.org/3/library/gc.html), [Rust Ownership](https://doc.rust-lang.org/book/ch04-01-what-is-ownership.html).
