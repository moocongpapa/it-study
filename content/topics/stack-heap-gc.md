## 익숙한 장면과 연결해요

스택은 일을 잠깐 맡기고 돌아올 순서를 적은 메모 더미, 힙은 여러 작업이 참조하는 공용 자료 보관실로 생각해 보세요. GC는 현재 업무에서 찾아갈 수 없는 자료를 찾아 정리하는 관리인과 비슷합니다.

## 선생님과 한 번 정리해요

함수가 다른 함수를 부르고 여러 객체를 만들 때 진행 상태와 데이터 수명을 관리해야 합니다. 정리되지 않는 데이터가 계속 쌓이면 메모리가 부족해질 수 있습니다.

## 여기서 연결해 봐요

프로그램은 실행 기록과 객체를 메모리에 보관하고, 더는 필요 없는 공간을 다시 사용할 수 있게 정리합니다.

왜 이런 순서가 필요한지 말로 설명할 수 있으면 좋아요. 코드와 자세한 설명은 아래에 준비했어요. 낯선 기호는 입력·바뀌는 값·결과로 나눠 읽어 봐요.

<!-- classroom-reference:start -->
추적 GC는 루트에서 연결을 따라 살아 있는 객체를 찾는다. 참조 카운팅은 참조 수로 수명을 관리하지만 순환 참조에는 추가 대응이 필요하다. 실제 런타임은 여러 기법을 섞고 세대·이동·동시 수집 등의 특성이 다르다.

Python 3의 순환 참조 관찰 예제다. 상세 수집 횟수는 버전에 따라 달라질 수 있다.

```python
import gc, weakref
class Item: pass
a, b = Item(), Item()
a.other, b.other = b, a
ref = weakref.ref(a)
del a, b
gc.collect()
assert ref() is None
```

스택 프레임에는 호출 상태와 참조가 있을 수 있고 참조의 대상은 별도의 객체일 수 있다. 언어의 escape analysis가 객체 배치를 바꾸기도 한다. C/C++에서는 할당·해제와 포인터 수명을, Rust에서는 소유권·차용 계약을, GC 언어에서는 루트 경로와 수집 비용을 이해해야 한다.

**실습:** 외부 리스트에 참조를 보관한 경우와 보관하지 않은 경우를 비교하자. 메모리 회수와 OS에 메모리를 즉시 반환하는 것도 같은 보장은 아니다.

## 해결 뒤에도 한 번 더

고친 다음 원래 입력으로 다시 확인하는 일을 **재검증**이라고 해요. 한 번 성공한 것만 보고 끝내지 않고, 비슷한 실패 조건에서도 괜찮은지 확인해요.

<!-- classroom-reference:start -->
가상 서버가 완료한 요청의 객체를 전역 추적 리스트에 계속 남긴다. GC 실행 횟수를 늘려도 그 객체는 도달 가능해 회수되지 않는다. 먼저 live heap, 할당률, RSS와 수집 후 객체 수를 구분한다.

**진단:** 힙 스냅샷에서 객체를 붙잡는 루트 경로를 확인하고 캐시·리스너·클로저·주기 작업이 수명을 늘리는지 본다. RSS만 보고 객체 누수라고 단정하지 않는다. allocator 예약 공간이나 파일 매핑도 영향을 준다.

**수정:** 캐시 크기·TTL·삭제 정책과 구독 해제를 명시한다. 객체를 무조건 풀링하면 살아 있는 메모리가 오히려 늘 수 있어 근거를 측정한다. 파일·소켓은 context manager나 명시적 close로 정리한다.

**재검증:** 요청 수를 반복 증가시켜 수집 후 생존 객체와 메모리가 일정 범위로 안정되는지 확인한다. GC pause 분포와 처리량을 함께 비교한다.

## 이유까지 말하면 더 좋아요

“나는 이 방법을 골랐어. 중요한 조건은 이것이고, 대신 이런 부담은 감수할게.”처럼 설명해 보세요. 그러고 나서 조건을 하나 바꾸면 같은 선택을 할지도 생각해 봐요.

<!-- classroom-reference:start -->
| 방식 | 강점 | 책임 |
|---|---|---|
| GC | 많은 객체 수명 관리 자동화 | 도달성 누수·pause·힙 예산 |
| 참조 카운팅 | 해제 시점 예측에 유리한 경우 | 순환·카운트 비용 |
| 소유권/RAII | 명시적인 수명과 자원 정리 | API 설계·소유권 복잡성 |
| 수동 할당 | 세밀한 제어 | 누수·이중 해제·use-after-free |

대규모 서버는 힙 최대값만 조정하지 않는다. 객체 할당률, 장수 객체 비율, 요청 동시성, 외부 자원을 포함한 메모리 예산을 정한다. pause 목표가 빡빡하면 런타임 수집기·데이터 구조·할당 패턴을 함께 비교한다.

**판단 연습:** 수명이 짧은 요청 객체 수백만 개와 장수 캐시를 같은 정책으로 관리할까? 수집 후 live set, p99 pause, RSS, 처리량을 선택 기준으로 삼자.
